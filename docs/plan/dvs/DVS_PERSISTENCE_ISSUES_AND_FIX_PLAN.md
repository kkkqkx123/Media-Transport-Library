# DVS 持久化问题清单与修复方案

## 背景

`dvs_agent` 使用 `SQLite kv` 表存放两个大 `JSON`（`node` 整机文档与六域 `config`），`dvs_platform` 使用通用文档表 `docs(kind,id,data)` 存放全部业务文档，另加 `tombstones` 与 `audit_log`。两者都把 `SQLite` 当作单机唯一可信存储，进程重启后依赖它恢复期望配置与事务状态。

## 问题清单

### Agent 侧

* 默认库路径在临时文件系统下，重启即丢失，与持久化目标矛盾。生产部署需要落到掉电不丢的目录，测试则继续使用显式传入的临时路径。
* `SQLite` 未做掉电与并发加固。缺少预写日志、忙等待超时与同步级别设置，异常断电或读写争用时容易出现锁冲突与损坏。
* 缺少库版本号，历史库只能靠个别字段特例回填，后续字段演进没有统一的迁移位置。
* 新库种子把在线态置为在线，首启即显得在线，不诚实。
* 启动时直接沿用上次落盘的易失运行态。在线标记、心跳时间、本机指标、当前播放与异常都是内存运行态，掉电重启后应回到离线与空值，等待引擎重探与平台心跳重建。能力探测结果作为缓存保留，避免引擎晚启动时无能力可用。
* 三处配置状态手工同步。单域状态同时存在于 `config` 表、聚合 `configStates` 与聚合 `configRevision`，每次变更都要多处同改，容易分叉。本次先保证落盘时三处同写，结构性拆分留待后续。

### Platform 侧

* 默认库路径同样在临时文件系统下，业务文档与事务快照重启即丢失。
* `SQLite` 同样缺少预写日志、忙等待超时与同步级别设置。心跳高频写与屏障事务共用同一连接与互斥锁，争用时更容易失败。
* 缺少库版本号，后续表结构演进没有统一位置。
* 操作审计日志只增不减。注册、心跳、上下线、布局分发、回滚、退役等全部写入 `audit_log`，长期运行必然膨胀。
* 节点文档每次心跳全量重写。注册与心跳合并整文档后整体落盘，写放大明显，且与 `op` 事务文档共用一张 `docs` 表。
* 跨文档引用只靠业务代码保证。绑定到墙与节点、场景到墙、白名单信号等关系没有数据库层约束，删除 Monta 墙与退役节点时靠路由层逐个检查，容易遗漏。

### 两侧共性

* 凭证与业务同文档存放。`Agent` 口令哈希与整机文档同一行存储，备份与导出天然带走凭证。
* 无备份与清理策略。除 `op` 终态回收与软删墙回收外，没有统一的库体积管理。

## 修复方案

### 路径与加固先行

* 两侧默认库路径迁出临时文件系统，落到掉电不丢的系统数据目录。命令行显式传入的路径优先级不变，现有单测使用的临时路径不受影响。
* 打开数据库前确保父目录存在，打开后设置忙等待超时，建表时启用预写日志与常规同步级别，并写入库版本号。预写日志等设置对内存库无害，失败只忽略，不阻断启动。
* 文档中记录的缺省路径随代码同步更新，避免文档与实现不一致。

### Agent 运行态与落盘语义

* 新库种子在线态置为离线，心跳时间置空，保持首启诚实。
* 启动加载时把易失运行态复位为离线与空值，能力探测结果保留为缓存。复位后回写一次，保证重启后落盘值不再残留过期在线态。
* 配置三态同写保持不变，后续再考虑把聚合视图改为按需派生，减少手工同步点。

### Platform 审计与回收

* 审计日志按条数上限滚动保留。每次写入后删除超出上限的最老记录，另在屏障清扫器的小时级回收中再兜底清理一次，保证长期运行体积有界。
* `op` 事务的恢复、超时置 blocked、崩溃窗口回滚重放、终态回收语义保持不变。本次不改变事务表与业务表共用 `docs` 的结构，只通过加固与清理降低争用与膨胀风险。
* 心跳全量重写本次不改写合并逻辑，先靠预写日志与忙等待缓解争用。差量合并与指标单列作为后续优化，待读写分离后再做。

### 暂不做事项

* 不拆 `Agent kv` 大文档结构，不拆 `Platform docs` 通用表结构。
* 不引入数据库层外键约束，引用完整性仍由业务代码保证。
* 不做备份导出脱敏与加密存储，凭证隔离作为后续专项。
