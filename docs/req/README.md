# DVS 项目需求整理与 MTL 基座实现分析

> 本文是 `docs/` 的总入口。输入有两个：工作区现有 DVS 需求文档（`00-overview`、`02-feature-map`、`03-requirements`、`04-ui-specs`、`05-tech-links`），以及基座项目 Media-Transport-Library（下称 MTL）。
>
> 分析基准：
> - MTL 仓库 `https://github.com/kkkqkx123/Media-Transport-Library`，提交 `b2d1988`，版本 `26.09.0.DEV`，许可证 BSD-3-Clause。
> - 本地分析副本位于 `/tmp/mtl`（临时目录，不进入本仓库）。
> - DVS 需求文档当前全部为 `draft`，本文同样为 `draft`，结论用于技术评审与排期，不替代真实产品、硬件、固件和测试签字。

## 1. 结论摘要

1. DVS 共有 11 条需求：7 条调度主线（分组、拼墙、设置、绑定、场景、开窗、清屏）、2 条节点本机需求（角色与信号、网络与运维）、1 条设备管理、1 条跨模块实时可靠性。
2. MTL 提供媒体数据面：SMPTE ST 2110-20 未压缩视频、ST 2110-22 压缩视频、ST 2110-30 音频、ST 2110-40 辅助数据、ST 2022-7 双路冗余、PTP、组播与流量整形。它覆盖“输入盒采集后上 IP、输出盒从 IP 收流后显示”的传输段。
3. MTL 不提供分组、拼墙、端口绑定、场景、开窗、播放任务、设备注册、节点本机后台和固件升级等业务能力，这些需要在平台服务和节点代理中自研。
4. MTL 仓库已经包含两个 RK3588 参考应用：`rk3588_end2end`（V4L2 采集 → RGA → MPP 编码 → MTL，反向解码 → DRM）和 `rk3588_mp4_dist`（ST2110-22/30 分发、多路接收、DRM 多平面合成、ALSA 播放）。这两个应用是 DVS 节点媒体引擎的直接起点。
5. 推荐总体架构为“平台控制面 + 节点代理 + MTL 媒体引擎”。视频在输入盒编码、以组播方式发送，输出盒按需加入组播并本地解码、裁剪、缩放、按图层合成后送 DRM 显示。
6. 千兆网络下推荐 ST 2110-22 压缩视频（H.264/HEVC 硬件编解码），万兆网络可选 ST 2110-20 未压缩视频。1080p60 未压缩约 3 Gbps，4K60 约 12 Gbps，千兆口无法承载。
7. 跨节点同帧的实现路径是：以 PTP 为统一时基，各输出节点在本地预先准备解码器和图层，平台下发统一 `apply_at`，所有节点在同一个全局帧边界切换本地合成布局。MTL 的 PTP、VSYNC 事件和用户 pacing 提供了基础能力。
8. 跨格窗口按“全局拼墙坐标系 → 每个节点本地视口片段”拆分。每个节点只渲染与自身格位相交的部分，使用 DRM plane 的源裁剪矩形和目标矩形完成无缝拼接。
9. 主要风险集中在六处：千兆带宽与画质/时延的取舍、H.264 GOP 导致场景切换等待关键帧、跨独立显示器同帧缺少实测证据、单节点 DRM 图层数量上限、ARM 平台只能软件 pacing、MTL 参考应用尚未产品化。
10. 建议按五个阶段推进：基座验证、媒体引擎 MVP、平台控制面、同帧与跨格、节点运维与规模化加固。先做两节点最小闭环，再扩到整墙。

## 5. 一句话定位

DVS 的业务复杂度在控制面，DVS 的技术风险在媒体面的“跨节点同帧 + 跨格拼接 + 千兆带宽约束”。MTL 解决传输与定时基础，产品化工作集中在节点媒体引擎和平台控制服务。
