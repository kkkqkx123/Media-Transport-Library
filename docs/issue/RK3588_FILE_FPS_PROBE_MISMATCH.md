# 文件片源帧率误读：r_frame_rate 与 avg_frame_rate 不一致【已规避】

日期：2026-11-09。板上实测（`/usr/local/test.mp4`，`live_ingest --source file`）。

## 1. 现象

- 用 ffprobe 读片源：`r_frame_rate=30/1`，看起来是 30fps 片。
  按 30fps 起 RX 会话后，链路能通但两端速率对不上：
  TX 日志探针行显示对齐到 24fps，会话按 24fps 建立。
- T1 首版按 30fps 判定供帧量，误报 TX 供帧不足
  （30 秒 730 帧，约 24.3fps）；改为 24fps 口径后供帧量恰为 24×30。

## 2. 根因

- 该 MP4 的容器平均帧率（avg_frame_rate）为 24fps，
  而原始码流帧率（r_frame_rate）标 30fps，二者不一致。
- 发送侧文件栈的探针对齐逻辑优先采用容器平均帧率
  （仅在配置为默认值 60 或未设置时），会话帧率、供帧节拍都按 24fps 走。
- 错不在发送侧：ST22 会话帧率必须等于实际供帧节拍，
  用码流标称值去对齐才是误读。RX 会话帧率同样必须等于 TX 会话帧率，
  因此 RX 也必须用探针值而非人工读到的标称值。

## 3. 修改方案（验证脚本侧，已落地）

- 不再人工指定 RX 帧率：脚本用 ffprobe 取同一片源的
  宽、高、平均帧率三元组，同时用于 RX 会话参数；
  TX 侧沿用发送栈的探针对齐，不在脚本里复写帧率。
- 判定口径改为供帧量约等于会话帧率乘时长（±10%，覆盖循环重开销），
  而不是与某个写死的帧率比较。
- 同一片源换片（如 23.976 或 25fps 片）无需改脚本，
  对齐自动跟随探针。

## 4. 验证

- T1 改后：探针三元组 1920x1080@24，TX 供帧 730/30 秒零丢弃，
  稳态窗口收流 480/480，误报消除。
- T2 沿用同一探针：文件 lane 会话 24fps 与 TX 会话一致，
  lane 产出 961/962。

## 5. 遗留

- 若片源本身 VFR 或平均帧率非 MTL 枚举值，会话创建会被拒绝。
  当前约束为只用 CFR 且帧率在枚举表内的片源做虚拟节点
  （与既有能力边界一致），碰到拒绝先查片源，不查链路。
