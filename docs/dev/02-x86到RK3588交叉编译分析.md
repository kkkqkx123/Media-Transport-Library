# x86 开发机 → RK3588 (aarch64) 交叉编译方案分析

本文在 `docs/dev/01-MTL编译体系分析.md`（下称“文档 01”）的基础上，分析如何在一台 x86_64 开发机上交叉编译出可在 RK3588（aarch64）上运行的 MTL 全栈：`libmtl`、patched DPDK、（可选）xdp-tools/libbpf、`MtlManager`、`RxTxApp`，以及两个 rk3588 参考应用 `e2e_app` / `mp4_dist_{tx,rx}`。

> **状态更新（2026-11-02）**：本方案已按 `docs/archive/RK3588_CROSS_COMPILE_PROGRESS.md` 全链路跑通（DPDK 729/729 → libmtl 52/52 → libxdp 1.6.3 → 两个 rk3588 应用），并在编译服务器 `devs` 完成正式 release 验证。本文保留为**方案分析 + 已验证参数的固化**；可执行的逐步命令见 `docs/dev/compile/5.10-debian-cross-compile.md`。文内所有“实际采用”的值均以已验证结果为准。

## 0. 一句话结论

可行，但仓库**没有任何现成的交叉编译支持**（无 cross file、`build.sh` 全程不传 cross 参数、`build_dpdk.sh` / `build_ebpf_xdp.sh` 均假设本机编译），因此正确做法是：**绕开 `build.sh`，手工按依赖顺序执行每一层 meson，每层都带同一个 aarch64 cross file**；板端专属依赖（MPP、RGA、内核 UAPI 头、板上的 FFmpeg/ALSA/DRM 版本）通过**从开发板导出的 sysroot** 提供，通用依赖（json-c、numa、libpcap 等）优先用 Debian multiarch 的 arm64 包补进同一 sysroot。

**已验证的关键变化（相对最初假设）**：

- 工具链采用 **ARM 官方 GNU Toolchain 13.3**（`aarch64-none-linux-gnu-*`，x86 宿主），**不**用 apt 的 `aarch64-linux-gnu-gcc`；
- 通过 **gcc/g++/pkg-config 包装脚本**（`aarch64-cc-wrap` / `aarch64-cxx-wrap` / `mtl-pkg-config`）统一注入 `--sysroot`、`-B`、`-L`、`-isystem`、`-Wl,-rpath-link`、`-lm`，并对 release 的 `-Werror` 降级未用变量类告警；
- **没有独立的 staging 目录**：patched DPDK、libmtl、libxdp 全部装进 sysroot（`DESTDIR=$SYSROOT`/`--prefix=/usr`），sysroot 同时是“板端库来源”与“构建产物安装目标”；
- 应用源码需要补 `#include <stdbool.h>`（约 40 个 `.c`），sysroot 需补 FFmpeg 未版本化 `.so` 软链。

最大的工程量不在 MTL 本身，而在 **sysroot 的组装与 DPDK 的交叉构建**。

## 1. 为什么不能直接用 `build.sh`

| 障碍 | 位置 | 说明 |
| --- | --- | --- |
| 无 cross file 机制 | `build.sh` | `meson setup build …` 未带 `--cross-file`，也没留任何注入点；环境变量开关（§1.2 文档 01）里没有工具链项 |
| DPDK 脚本本机构建 | `script/build_dpdk.sh` | `meson build`（DPDK 自身目录）不带 cross file；其“已安装版本检测”用 `pkg-config libdpdk`，交叉环境下宿主机的 x86 `libdpdk.pc` 会污染判断 |
| xdp-tools 脚本本机构建 | `script/build_ebpf_xdp.sh` | 内部用 `cc -dumpmachine` 探测架构（`build_ebpf_xdp.sh:139`），本机得到 x86_64，产物是宿主架构 |
| MtlManager 的 BPF 编译 | `manager/meson.build` | 找到 libxdp+libbpf 时强制要求 `clang` + `llvm-strip`。BPF 目标本身架构无关（不需要 aarch64 clang target），但链接 `mtl.xdp.o` 进管理进程的 libbpf 调用要走 sysroot 的 libbpf 头 |
| 单测无法执行 | `./build.sh unit` | 交叉编译出的 `UnitTest` 是 aarch64 二进制，x86 上不能跑（除非配 qemu-user）。`build.sh unit` 模式“构建并直接运行后退出”，交叉场景必须只构建不运行 |

结论：交叉编译是**逐层手工 meson**，`build.sh` 只能当作“每层该做什么”的操作清单参考（文档 01 §1.2），不能直接执行。

## 2. 总体布局

在开发机上建一个独立工作区（下称 `$WS`），四棵树分工：

```
$WS/
├── toolchain/              # 交叉工具链（ARM GNU Toolchain 13.3，x86 宿主）
├── sysroot/                # aarch64 的头文件 + 库（核心工作，也是安装目标）
├── aarch64.ini             # meson cross file（MTL / app 层共用；实际放在 sysroot/aarch64.ini）
└── src/
    ├── dpdk-26.07/         # patched DPDK 源码（按文档 01 §2 流程取补丁）
    ├── xdp-tools-1.6.3/    # 仅 AF_XDP 路线
    └── Media-Transport-Library/
```

最终产物安装进 `$WS/sysroot`（相当于板上的 `/usr`），部署时整棵 rsync 到板子。

### 2.1 实际采用的两台机器布局（已验证）

| 角色 | 主机 | OS | 工作区 |
| --- | --- | --- | --- |
| 编译服务器 | `devs`（`ssh devs`） | Ubuntu 18.04 x86_64 | `/data/kkkqkx/mtl/`（正式大规模构建） |
| 本地镜像 | 本地 x86_64 | Arch Linux | `/home/kkkqkx/code/mtl/`（或 `/home/kkkqkx/mtl/`，见 §2.2 路径注意） |

工具链：`/data/kkkqkx/arm-gnu-toolchain-13.3.rel1-x86_64-aarch64-none-linux-gnu`（devs）/ `/home/kkkqkx/arm-gnu-toolchain-13.3.rel1-x86_64-aarch64-none-linux-gnu`（本地）；meson/ninja 来自 buildroot host `…/host/bin` 或系统安装。

### 2.2 meson cross file（`$WS/sysroot/aarch64.ini`，已验证版）

```ini
[binaries]
c = '/home/kkkqkx/mtl/bin/aarch64-cc-wrap'
cpp = '/home/kkkqkx/mtl/bin/aarch64-cxx-wrap'
ar = 'aarch64-none-linux-gnu-ar'
strip = 'aarch64-none-linux-gnu-strip'
pkg-config = '/home/kkkqkx/mtl/bin/mtl-pkg-config'

[host_machine]
system = 'linux'
cpu_family = 'aarch64'
cpu = 'armv8-a'          # 不用 'rk3588' / 'native'；RK3588 是 ARMv8.2-A，generic 路线用 armv8-a 最稳
endian = 'little'

[properties]
platform = 'generic'
c_args = ['--sysroot=/home/kkkqkx/mtl/sysroot',
          '-isystem/home/kkkqkx/mtl/sysroot/usr/include/aarch64-linux-gnu']
c_link_args = ['--sysroot=/home/kkkqkx/mtl/sysroot',
               '-B/home/kkkqkx/mtl/sysroot/usr/lib/aarch64-linux-gnu',
               '-L/home/kkkqkx/mtl/sysroot/usr/lib/aarch64-linux-gnu',
               '-L/home/kkkqkx/mtl/sysroot/lib/aarch64-linux-gnu']
cpp_args = c_args
cpp_link_args = c_link_args
```

说明：

- `pkg-config` 指向 **包装脚本** `mtl-pkg-config`，强制 `PKG_CONFIG_SYSROOT_DIR`/`PKG_CONFIG_LIBDIR` 锁定 sysroot，杜绝 buildroot 的 pkg-config 泄漏；
- `c`/`cpp` 指向包装脚本，每次调用自动追加 `--sysroot` + `-B` + `-L`(×2) + `-isystem` + `-Wl,-rpath-link`(×2) + `-lm`，并把 `-Werror` 的未用变量类告警降级（见 §4.3）；
- `--sysroot` 必须用**绝对路径**，meson cross file 不展开 `~` 和相对路径；
- DPDK 与 xdp-tools 不是 meson 之外的独立体系——DPDK 本身就是 meson 工程，**复用同一份 cross file**；xdp-tools 是 GNU make 体系，走各自的交叉变量（§4.2）；
- **路径注意**：包装脚本与 cross file 硬编码 `/home/kkkqkx/mtl/...`。本地实际工作树在 `/home/kkkqkx/code/mtl/`，需保证 `/home/kkkqkx/mtl` 可用（建符号链接或 sed 替换路径）；devs 上对应为 `/data/kkkqkx/mtl/`。

### 2.3 包装脚本内容（已验证）

`aarch64-cc-wrap`：

```sh
#!/bin/sh
REAL=/home/kkkqkx/arm-gnu-toolchain-13.3.rel1-x86_64-aarch64-none-linux-gnu/bin/aarch64-none-linux-gnu-gcc
SYSROOT=/home/kkkqkx/mtl/sysroot
exec "$REAL" --sysroot="$SYSROOT" \
  -B"$SYSROOT/usr/lib/aarch64-linux-gnu" \
  -L"$SYSROOT/usr/lib/aarch64-linux-gnu" -L"$SYSROOT/lib/aarch64-linux-gnu" \
  -isystem"$SYSROOT/usr/include/aarch64-linux-gnu" "$@" \
  -Wno-error=unused-variable -Wno-error=unused-but-set-variable \
  -Wl,-rpath-link,"$SYSROOT/usr/lib/aarch64-linux-gnu" \
  -Wl,-rpath-link,"$SYSROOT/lib/aarch64-linux-gnu" -lm
```

`aarch64-cxx-wrap` 同构（g++）。`mtl-pkg-config` 强制 `PKG_CONFIG_SYSROOT_DIR=$SYSROOT` 与 `PKG_CONFIG_LIBDIR=$SYSROOT/...`。

## 3. sysroot：需要从开发板获取什么

sysroot 组装是整个方案里最繁琐、最容易踩坑的一步。原则：**“板上跑的每一个 `.so`，交叉链接时都要能找到同版本的 `.so` 和头文件”**。

### 3.1 必须来自开发板的（BSP 专属，multiarch 仓库没有）

| 内容 | 板上路径（典型） | 用途 |
| --- | --- | --- |
| Rockchip MPP 头 + `librockchip-mpp.so` | `/usr/include/rockchip/`、`/usr/lib/aarch64-linux-gnu/librockchip-mpp*` | `rockchip_mpp` pkg-config（end2end P3/P4、mp4_dist RX 解码） |
| RGA 头 + `librga.so` | `/usr/include/rga.h`（或 `im2d.h`）、`librga.so` | `librga` pkg-config |
| 板上 FFmpeg（4.4 系，`libavformat 58.45.100`） | `/usr/lib/aarch64-linux-gnu/libav*` | `libavformat/avcodec/avutil`。`versions.env` 钉 7.0，但板端是 4.4；已接受发行版版本（RB15） |
| 内核 UAPI 头（V4L2、DRM 用户接口） | `/usr/include/linux/`、`/usr/include/linux/videodev2.h` 等 | 来自板上的 `linux-libc-dev` 或 BSP 内核头包；**用板上版本而不是宿主机的 x86 linux-libc-dev** |
| `libasound.so.2` + alsa 头 | `/usr/include/alsa/` | `alsa` pkg-config（mp4_dist RX 音频） |

导出方式（在板上执行，回传到 `$WS/sysroot`）：

```bash
# 板上：打包根文件系统里的头与库（不拷整个 rootfs）
sudo tar czf /tmp/rk3588_sysroot.tar.gz \
  /usr/include \
  /usr/lib/aarch64-linux-gnu \
  /usr/lib/pkgconfig /usr/share/pkgconfig \
  /lib/aarch64-linux-gnu \
  /usr/local/include /usr/local/lib
# 开发机：解到 sysroot/
```

**符号链接是 sysroot 的头号坑**：`libc.so`、`libm.so` 等链接脚本/软链指向绝对路径 `/lib/aarch64-linux-gnu/...`，不重写会让交叉链接器悄悄用上 x86 的同名库。实际共改写 **48 处**绝对软链为相对链（见 `docs/dev/compile/5.10-debian-cross-compile.md` §4.2）。至少要在链接产物上抽查 `readelf -d` 确认没有把 x86 库链进去。

### 3.2 可以从宿主机 multiarch 仓库补的（开发板与发行版同源时）

Ubuntu/Debian 支持直接下载 arm64 deb 而不安装（避免真装 multiarch 污染宿主）：

```bash
apt-get download \
  libjson-c-dev:arm64 libnuma-dev:arm64 libpcap-dev:arm64 \
  libssl-dev:arm64 libdrm-dev:arm64 libasound2-dev:arm64 \
  libelf-dev:arm64 zlib1g-dev:arm64
for d in *.deb; do dpkg-deb -x "$d" $WS/sysroot/; done
```

要点：

- **与板子同一个发行版基座**（板上 Debian 11 bullseye 就用 bullseye 的 arm64 deb），版本错配会以运行时符号缺失的形式爆出来；
- `libdrm-dev` 若发行版版本与板上 BSP 有出入，以板上导出的那份为准，multiarch 包只作兜底；
- `libnuma-dev` 在 Debian 11 **不提供 `numa.pc`**（只给 `numa.h` + `libnuma.so`）。DPDK 交叉构建靠 `find_library('numa')` + `has_header('numa.h')` 兜底，无需 `.pc`；
- `libjson-c-dev`、`libnuma-dev`、`libpcap-dev` 是 MTL 库层 + RxTxApp/app 层的必需项（文档 01 §3.1、§4 表）。

### 3.3 交叉编译自产的（构建顺序产物，回填 sysroot）

| 产物 | 装到 | 下游消费者 |
| --- | --- | --- |
| patched DPDK（`libdpdk.pc` + 头） | `$WS/sysroot`（`DESTDIR=$SYSROOT`，`--prefix=/usr`） | libmtl、所有下游 |
| xdp-tools/libbpf（`libxdp.pc`、`libbpf.pc`） | `$WS/sysroot` | libmtl（`MTL_HAS_XDP_BACKEND`）、MtlManager |
| `libmtl` + `mtl.pc` | `$WS/sysroot`（`--prefix=/usr`） | app、manager、RxTxApp、两个 rk3588 应用 |
| （可选）FFmpeg 7.0 arm64 | `$WS/sysroot` | mp4_dist、st22 场景 |

即：`mtl.pc`、`libdpdk.pc` 等**不需要**从板上拿——它们本来就由交叉构建自己产生，装进 sysroot 后由 `PKG_CONFIG_PATH` 暴露给下游。**没有独立 staging 目录**。

### 3.4 pkg-config 三件套（每一层构建都要导出）

```bash
export PKG_CONFIG_SYSROOT_DIR=$WS/sysroot
export PKG_CONFIG_LIBDIR=$WS/sysroot/usr/lib/pkgconfig:$WS/sysroot/usr/share/pkgconfig:$WS/sysroot/usr/lib/aarch64-linux-gnu/pkgconfig
export PKG_CONFIG_PATH=$WS/sysroot/lib/pkgconfig:$WS/sysroot/lib/aarch64-linux-gnu/pkgconfig
```

- `PKG_CONFIG_LIBDIR` **必须显式覆盖**，否则宿主的 `/usr/lib/x86_64-linux-gnu/pkgconfig` 会漏进来，`json-c.pc` 之类的名字会命中 x86 版本——这是交叉编译最常见的静默错误源；
- 自产 `.pc`（mtl/libdpdk）里若有 `prefix=/usr` 之类绝对路径，配合 `PKG_CONFIG_SYSROOT_DIR` 通常已够用。

## 4. 各层交叉构建步骤（顺序即依赖序）

### 4.1 patched DPDK（必做，不能省）

用 `script/build_dpdk.sh` 只取源码与补丁（文档 01 §2），交叉构建手工做：

```bash
# 1) 取源码 + 打补丁（可借用脚本逻辑，或手工）
curl -LO https://fast.dpdk.org/rel/dpdk-26.07.tar.xz
tar xf dpdk-26.07.tar.xz && cd dpdk-26.07
for p in $MTL_REPO/patches/dpdk/26.07/*.patch; do patch -p1 -i "$p"; done

# 2) 交叉配置（DPDK 自己也是 meson 工程，复用 aarch64.ini）
meson setup build-aarch64 --cross-file $WS/sysroot/aarch64.ini \
  -Dplatform=generic \
  -Dcpu_instruction_set=armv8-a \
  -Denable_drivers=net/null,net/af_xdp,bus/pci,bus/vdev,common/iavf \
  -Dtests=false -Dexamples= \
  --prefix=/usr
ninja -C build-aarch64 && DESTDIR=$WS/sysroot ninja -C build-aarch64 install
```

要点与风险：

- **NUMA 头必须在 sysroot**（`numa.h` 来自 `libnuma-dev:arm64`），否则 DPDK configure 失败；
- `-Dplatform=generic`：RK3588 不是 DPDK 认知的 SoC，generic + `cpu_instruction_set=armv8-a` 最稳；不要用 native；
- 驱动精简是可选优化；文档 01 §2 的结论不变：即使走 AF_XDP/kernel 数据面，DPDK 的 EAL/mbuf/ring/ethdev API 仍被 libmtl 大量使用，**库本体必须完整链接**；
- `script/build_dpdk.sh` 的“已安装版本检测”在交叉场景直接跳过整个脚本即可——宿主机 pkg-config 环境已指向 sysroot，检测语义也就自然对了；
- x86 的 ice/iavf 内核驱动补丁（`script/build_drivers.sh`）与交叉无关，跳过；
- 已验证结果：**729/729，0 错误**。

### 4.2 xdp-tools + libbpf（仅 AF_XDP 路线）

xdp-tools 是 make 体系，交叉方式（已验证，动态链接 sysroot 的 libbpf 1.4.0，**不**用子模块 1.6）：

```bash
cd xdp-tools-1.6.3
export PKG_CONFIG=/…/bin/mtl-pkg-config \
       CC=/…/bin/aarch64-cc-wrap CLANG=/usr/sbin/clang \
       BPF_TARGET=bpf PREFIX=/usr
./configure
make -C lib/libxdp libxdp.so libxdp.pc        # 仅 .so + .pc
# 装入 sysroot：libxdp.so.1.6.0 + 软链、headers/xdp/*.h、libxdp.pc（libdir 修正为 /usr/lib/aarch64-linux-gnu）
```

- libbpf/xdp-tools 内部的 BPF 程序编译用 clang（BPF 目标架构无关），用户态库用交叉 gcc；需要 sysroot 里有 `libelf`（libbpf 依赖，前面 deb 里已备）；
- 若板上 RK3588 内核的 BPF 能力不足（老 BSP 内核），可先退回 `kernel:` socket 数据面，跳过本步，libmtl 会静默降级为无 AF_XDP 后端——但**构建后必须断言是否真的编进了后端**（文档 01 RB2）：`grep MTL_HAS_XDP_BACKEND <build>/config.h`；
- 当前未编 `xdp-dispatcher.bpf.o`（运行期默认 dispatcher）；若 RK3588 路线需要，本地 clang 已支持 `-target bpf` 可补编；
- 本步完成后 `libxdp.pc`/`libbpf.pc` 在 sysroot，`PKG_CONFIG_PATH` 已覆盖。

### 4.3 libmtl（核心）

```bash
cd Media-Transport-Library
meson setup build-aarch64 --cross-file $WS/sysroot/aarch64.ini \
  --prefix=/usr \
  -Dbuildtype=release \
  -Denable_usdt=false        # USDT 默认开但 sysroot 无 sys/sdt.h，关闭不影响功能
ninja -C build-aarch64 && DESTDIR=$WS/sysroot ninja -C build-aarch64 install
grep -q MTL_HAS_XDP_BACKEND build-aarch64/config.h && echo "XDP backend ENABLED" || echo "XDP backend OFF"
```

要点与风险：

- **MPOL_LOCAL 未定义**：sysroot 的 `numaif.h` 补 `#include <linux/mempolicy.h>`（与新版 glibc 一致，带 include guard），否则编译失败；
- **release `-Werror` 与 USDT-off 冲突**：USDT 关闭留下 `usdt_stat`/`rtp_ts`/`idx`/`meta_num_before_reset` 未用变量告警 → 在包装脚本 `"$@"` **之后**追加 `-Wno-error=unused-variable -Wno-error=unused-but-set-variable`（仅降级这一类、保留 `-O2` 与其余 `-Werror`）；
- **SIMD 探测自然退化**：meson 会探测 `-msse4.2/-mavx2/-mavx512*`，aarch64 gcc 一律拒绝，flag 不进命令行；`st_avx2.c`/`st_avx512*.c` 被 `#ifdef MTL_HAS_AVX2` 包裹，交叉下编译为空翻译单元（文档 01 §3.2），颜色转换走标量路径。**验证**：configure 日志中不应出现任何 `MTL_HAS_AVX*`；
- `-Denable_tests=false` 可选：gtest 不交叉（Cannot run test；如需单测见 §6）；gtest 头需 `libgtest-dev:arm64` 补进 sysroot，但**不能运行**；
- 产物：`$WS/sysroot/usr/lib/aarch64-linux-gnu/libmtl.so`、`$WS/sysroot/usr/include/`、`mtl.pc`；
- 已验证结果：**52/52，0 错误**（release，`-Werror` 降级未用变量类告警），`libmtl.so` NEEDED 含 `libxdp.so.1`。

### 4.4 FFmpeg 7.0（仅 mp4_dist 需要；TX 想在 x86 上单独跑则不需要交叉版）

实际采用 **选项 1（接受板上发行版 FFmpeg 4.4）**：sysroot 已带 `libavformat 58.45.100`/`libavcodec 58.91.100`/`libavutil 56.51.100`，构建可过；API 差异（如有）需据 `mp4_dist` 代码自查。为让 `-lavformat` 解析，需补齐**未版本化** `libavformat.so`/`libavcodec.so`/`libavutil.so` 软链（从板拷贝时符号链接被压平所致，与 MPP/RGA 同源）。

若严格对齐 7.0：x86 上 `./configure --enable-cross-compile --target-os=linux --arch=aarch64 --cross-prefix=aarch64-none-linux-gnu- --sysroot=$WS/sysroot --prefix=$WS/sysroot --enable-shared --disable-static --disable-x86asm` 后 make install。工作量可控（FFmpeg 官方支持交叉），但注意配套的编解码器开关按需裁剪。

### 4.5 MtlManager（AF_XDP 路线必做）

```bash
cd manager
meson setup build-aarch64 --cross-file $WS/sysroot/aarch64.ini \
  --prefix=/usr
ninja -C build-aarch64 && DESTDIR=$WS/sysroot ninja -C build-aarch64 install
```

- 宿主机的 `clang` + `llvm-strip` 继续用于把 `mtl.xdp.c` 编成 `mtl.xdp.o`（BPF 与目标机架构无关），但 libbpf 头/库来自 sysroot；
- 若跳过 xdp-tools（§4.2 不做），MtlManager 会因找不到 libxdp/libbpf 而走无 XDP 分支，不需要 clang——此时 `mtl.xdp.o` 不会生成，板上 AF_XDP 后端自然不可用（与 RB2 一致，属预期）；
- 注意：当前未编 `xdp-dispatcher.bpf.o`（运行期默认 dispatcher），RK3588 路线需要时可补编。

### 4.6 两个 rk3588 应用（真正的交付物）

```bash
cd app/rk3588_end2end
meson setup build-aarch64 --cross-file $WS/sysroot/aarch64.ini && ninja -C build-aarch64

cd ../rk3588_mp4_dist
meson setup build-aarch64 --cross-file $WS/sysroot/aarch64.ini \
  -Dbuild_tx=true -Dbuild_rx=true && ninja -C build-aarch64
```

- 依赖全部经 §3.4 的 pkg-config 环境解析：`mtl`/`libdpdk` 来自 sysroot，`rockchip_mpp`/`librga`/`libdrm`/`alsa`/FFmpeg 来自 sysroot；
- **必须做产物断言**（RB5/RB16 在交叉下加倍成立）：`test -x app/rk3588_end2end/build-aarch64/e2e_app` 等。交叉环境下“依赖缺失静默跳过”更容易发生（sysroot 少一个 `.pc` 都会触发），只看 `ninja` 退出码会漏检；
- `mp4_dist` 的 `build_rx=true` 带的 MPP 链接测试（`cc.links`）此时跑的是**交叉 gcc + sysroot**，是验证 MPP 头/库是否正确进 sysroot 的天然检查点——若这里失败，回查 §3.1 的导出与软链接改写；
- **应用源码缺 `#include <stdbool.h>`**：交叉环境下 `bool`/`true`/`false` 不再被间接引入（板端原生编译碰巧引入）。已在两个应用约 40 个 `.c` 顶部补 `#include <stdbool.h>`（标准头、幂等、不影响原生构建）。**这是源码改动，建议提交**；
- 每个应用各自的 `meson.build` 里没有 cross 感知逻辑，但也没有 x86 硬编码（与 `st22_avcodec` 的 `-msse4.2` 硬编码不同，见 RB4——该插件在交叉场景**明确跳过，不要编**）。

已验证依赖版本（全部 `found`）：

- end2end：`libdrm` / `threads` / `rockchip_mpp 1.3.9` / `mtl 26.09` / `json-c 0.15` / `librga 2.1.0`；
- mp4_dist（TX+RX）：`mtl` / `libavformat 58.45` / `libavcodec 58.91` / `libavutil 56.51` / `json-c` / `rockchip_mpp`（含 **link test: YES**）/ `libdrm` / `alsa 1.2.4`。

已验证产物：

- end2end：23/23，0 错误 → `e2e_app`/`test_pipeline`/`test_io`/`test_codec`/`test_hal`/`test_sps_vui`（ARM aarch64）；
- mp4_dist：57/57，0 错误 → `mp4_dist_tx`/`mp4_dist_rx`/`rx_minimal` 及测试（`mp4_dist_rx` NEEDED 含 libmtl/libasound/libavformat/libavcodec/librockchip_mpp/libdrm）。

### 4.7 RxTxApp（验收框架用，可选）

`tests/tools/RxTxApp/` 是独立 meson 工程，交叉方式同 §4.6；产物是 aarch64 二进制，部署到板上供 pytest 验收框架（跑在 x86 宿主，通过 SSH 驱动板子）使用。注意它链接 `json-c`、`pcap`、可选 `sdl2`——**SDL2 交叉版很麻烦且板上无需显示**，可接受它静默跳过（对照文档 01 §4 表确认无强依赖）。

## 5. 部署到板子

```bash
# sysroot 整树 rsync（假设板上放 /opt/mtl-arm）
rsync -a $WS/sysroot/ board:/opt/mtl-arm/
# 板上运行时环境
export LD_LIBRARY_PATH=/opt/mtl-arm/usr/lib/aarch64-linux-gnu:/opt/mtl-arm/lib/aarch64-linux-gnu
# DPDK 运行期（hugepages/AF_XDP 权限）仍按 doc/run.md / MtlManager 流程，交叉不改变运行期约束（文档 01 RB10）
```

验证产物架构：`file staging/**/*`（或抽查关键二进制）应为 `ELF 64-bit LSB ... ARM aarch64`；`readelf -d e2e_app | grep NEEDED` 确认没有混入 x86 库名。

板端运行时依赖：应用运行于 RK3588 时，需板端具备 libmtl.so 及其 NEEDED（DPDK/libbpf/libxdp 已在 sysroot；FFmpeg 的私有依赖 xml2/bz2/gnutls 等由 libavformat.so 自身拉取，板端已具备）。

## 6. 测试怎么办

| 层级 | 交叉下的可行性 |
| --- | --- |
| 单元测试（`build.sh unit`） | 可交叉**构建**，不能在本机**运行**。要跑就上 `qemu-user`（`qemu-aarch64 -L $WS/sysroot ./UnitTest`，配合 `-static` 或让 qemu 走 sysroot 的 ld-linux），CI 可行但工程量另计；P0 建议仍按文档 01 §6.1 口径在板上原生编译跑单测 |

## 7. 新增风险登记（承接文档 01 §7 的 RB 系列）

| ID | 风险 | 应对 |
| --- | --- | --- |
| RB11 | sysroot 软链接污染 | 绝对链接未改写时可能链到宿主 x86 库且**不报错**。导出脚本必须改写软链；产物用 `readelf -d` 抽查 NEEDED（实际改写 48 处） |
| RB12 | pkg-config 宿主泄漏 | `PKG_CONFIG_LIBDIR` 忘记覆盖时，`json-c` 等命中 x86 `.pc`，链接器报 architecture mismatch 或静默失败。构建前 `PKG_CONFIG_LIBDIR=… pkg-config --variable=libdir json-c` 验证 |
| RB13 | aarch64 gcc 新告警 × `-Werror` | 首次交叉失败几乎必然。用 `debugonly` 先收集告警清单，修完再回 release；或在包装脚本追加 `-Wno-error=unused-variable -Wno-error=unused-but-set-variable` |
| RB14 | DPDK 版本检测被宿主 `libdpdk.pc` 干扰 | 交叉流程完全绕开 `build_dpdk.sh`，只借用它取源码+补丁（§4.1） |
| RB15 | 板上 FFmpeg 版本 ≠ versions.env 钉的 7.0 | 已接受发行版 4.4（`libavformat 58.45.100`）；API 差异需据 `mp4_dist` 自查，或交叉自编 7.0（§4.4） |
| RB16 | 依赖缺失静默跳过（RB5 交叉放大版） | sysroot 缺 `.pc` 时 end2end 静默不生成 `e2e_app`。构建脚本强制产物存在性断言（§4.6） |
| RB17 | 交叉构建无 CI 背书（RB1 的交叉放大版） | 首次打通后把整条命令序列固化成脚本（如 `script/cross_build_rk3588.sh`）入库，锁版本、留日志 |
| RB18 | RK3588 BSP 内核 BPF 能力不足导致 AF_XDP 后端白编 | 构建后断言 `MTL_HAS_XDP_BACKEND`；不可用则退化 `kernel:` 后端，MtlManager 相应不带 `mtl.xdp.o` |
| RB19 | `MPOL_LOCAL` 未定义 | sysroot 的 `numaif.h` 补 `#include <linux/mempolicy.h>`（带 include guard） |
| RB20 | 应用源码 `bool`/`true`/`false` 不再被间接引入 | 在约 40 个 `.c` 顶部补 `#include <stdbool.h>`（标准头、幂等） |
| RB21 | FFmpeg 未版本化 `.so` 软链缺失 | 从板拷贝时符号链接被压平，需手动补齐 `libavformat.so`/`libavcodec.so`/`libavutil.so` |
| RB22 | 包装脚本/cross file 路径硬编码 | `/home/kkkqkx/mtl/...` 与实际工作树 `/home/kkkqkx/code/mtl/...` 不一致时构建找不到 sysroot；建符号链接或 sed 替换 |
| RB23 | libxdp 默认 dispatcher BPF 对象未编 | `xdp-dispatcher.bpf.o` 当前未编；RK3588 路线需要时用 clang `-target bpf` 补编 |
| RB24 | 源码改动待提交 | 应用 `stdbool.h` 补 include 是真正的代码改动，建议 commit |
