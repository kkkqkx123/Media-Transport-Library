# RK3588 6.1 内核完整编译与产物参考

## 0. 目标与范围

在 devs（`/data/kkkqkx/rk3588bsp`，Ubuntu 18.04 x86_64）上，从 Rockchip 6.1 SDK **全量编译**出自洽的 6.1 `update.img`（含 MiniLoader / uboot【内含 trust/ATF/TEE】/ misc / boot【6.1 内核】/ recovery / oem / userdata / rootfs），内核打开 AF_XDP/eBPF/BTF/大页，供 RK3588 cm588 板卡**整包烧录**。

实测基线：SDK 提交 `98e7f9606`（AF_XDP/eBPF）+ `6b4e691d6`（构建修复：关闭 `CONFIG_STMMAC_UIO`）；产物内核版本 **`6.1.118`**（编译者 `itc@itc`）。

> 内核单独编译的逐步指南见 `docs/dev/compile/RK3588_6.1_KERNEL_BUILD.md`；本文档偏重「完整编译的坑 + 验证方法 + 产物路径」，作为后续速查参考。

## 1. 完整编译必须注意的问题（坑）

### 1.1 主机依赖：`pahole`(dwarves) 与 `libelf-dev` 是构建期硬依赖
- `CONFIG_DEBUG_INFO_BTF=y` → 需要主机 `pahole`：`sudo apt install dwarves`。
- `resolve_btfids`（BTF 工具，构建期由内核 tree 编译）需要主机 `libelf-dev`：`sudo apt install libelf-dev`。
  缺它会 `fatal error: libelf.h: No such file or directory`，`btf.o`/`libbpf.o`/`linker.o`/`usdt.o` 报错，内核编译中止。
- 旧版构建指南漏列 `libelf-dev`，实测**必须**。详见编译指南 §2。

### 1.2 Mali CSF 固件必须手动复制（且不进 patch）
- `CONFIG_MALI_VALHALL=y` 把 Mali 驱动编为内置，其 `mali_kbase_csf_firmware.c` 用 `.incbin "mali_csffw.bin"` 把固件直接链入内核镜像。
- 该 `.bin` 被 `kernel-6.1/.gitignore` 的 `*.bin` 忽略，仓库内不存在，编译前必须：
  ```bash
  cp external/libmali/firmware/g610/mali_csffw.bin kernel-6.1/drivers/gpu/arm/valhall/mali_csffw.bin
  ```
- 它不是 git 跟踪文件，**不进 `patches/rk3588`**；应用 patch 后、编译前需自行放置。

### 1.3 `CONFIG_STMMAC_UIO` 必须关闭
- 基础 SDK 的 `stmmac_uio.c` 引用 6.1 已移除的 `stmmac_priv` 成员，内核本体编译失败。
- 已在 `ztl_defconfig` 关闭（提交 `6b4e691d6`）。详见编译指南 §5。

### 1.4 只编内核 ≠ 能出 `update.img`（最关键）
- `./build.sh kernel-6.1` 只产出 `boot.img`，**不会**生成 MiniLoader / uboot / trust / rootfs。
- 要整包 `update.img`，必须跑**全量** `./build.sh`（或分别 `./build.sh loader uboot trust kernel rootfs` 后再 `./build.sh firmware && ./build.sh updateimg`）。
- 本 SDK 初次全量构建实测耗时 **~2.5 小时**：buildroot 主 rootfs 与 recovery rootfs 各自从零引导一套交叉工具链，recovery 阶段最慢（gcc/glibc bootstrap）。

### 1.5 本板没有独立 `trust` 分区（正常现象，别慌）
- cm588 的 `package-file` 与 `parameter.txt` 分区表只有 `uboot/misc/boot/recovery/backup/userdata/oem/rootfs`，**没有 trust 分区**。
- RK3588 的 BL31/ATF 与 TEE 已打包进 `uboot.img`（`u-boot/` 下 `bl31.elf`/`tee.bin` 即来源）。因此 `output/firmware/` 里看不到 `trust.img` 是预期。

### 1.6 内核 defconfig 来源
- `device/rockchip/common/configs/Config.in.kernel` 中 `RK_KERNEL_DEFCONFIG` 默认 `ztl_defconfig`，全量 `./build.sh` 也会用我们带 AF_XDP 的 `ztl_defconfig`，不会丢配置。

### 1.7 其他
- `CONFIG_WERROR=y`：用 SDK 自带 gcc 10.3 交叉编，别用主机 gcc。
- `kernel` 是软链到 `kernel-6.1`；打 patch 用 `kernel-6.1/` 全路径。
- 构建不污染 git：`output/`、`*.img`、`Image`、`.config` 均被各级 `.gitignore` 覆盖（除 `kernel-6.1/tools/bpf/resolve_btfids/libsubcmd/` 这一构建中间目录会显示为 untracked）。

## 2. 完整编译执行命令

```bash
cd /data/kkkqkx/rk3588bsp

# 1) 选板级配置（首次 / 切板）
./build.sh rockchip_rk3588_ztl_cm588_defconfig

# 2) 放 Mali 固件（见 §1.2）
cp external/libmali/firmware/g610/mali_csffw.bin \
   kernel-6.1/drivers/gpu/arm/valhall/mali_csffw.bin

# 3) 全量构建：loader + uboot + trust + rootfs + kernel，末尾自动打包 firmware 与 update.img
./build.sh

# 若仅想重打镜像（不重编）：
#   ./build.sh firmware && ./build.sh updateimg
```

### 2.1 后台运行 + 轮询（推荐，避免会话断开杀进程）
```bash
# 完全脱离会话启动（setsid），日志落盘
setsid bash -c "./build.sh > build_full.log 2>&1" < /dev/null &

# 轮询：每 60s 打一次心跳；检测到 update.img 或进程退出即止
for i in $(seq 1 200); do
  sleep 60
  tail -3 build_full.log
  [ -f output/firmware/update.img ] && { echo UPDATEIMG_DONE; break; }
  pgrep -f "build.sh" >/dev/null || { echo BUILD_PROC_GONE; tail -30 build_full.log; break; }
done
```
> 注意：远端 `sleep` 期间无输出会触发 idle 超时，轮询循环里用 `echo`/心跳即可避免。本次实测用此法在断开的 ssh 会话下仍跑完。

## 3. 验证方式（确认内核特性真的进了镜像）

### 3.1 产物侧验证（在 devs）
```bash
# 内核版本（嵌在 boot.img 里）
strings -n 6 output/firmware/boot.img | grep -m1 "Linux version"   # 期望 6.1.118

# 关键配置（全量构建用的 .config）
grep -E "^CONFIG_XDP_SOCKETS=|^CONFIG_XDP_SOCKETS_DIAG=|^CONFIG_BPF_SYSCALL=|^CONFIG_BPF_JIT=|^CONFIG_BPF_JIT_ALWAYS_ON=|^CONFIG_CGROUP_BPF=|^CONFIG_HUGETLBFS=|^CONFIG_DEBUG_INFO_BTF=|^CONFIG_YT6801=" kernel-6.1/.config
#   → 以上应全部 =y

# FIT 内容
rkbin/tools/mkimage -l output/firmware/boot.img
#   → 应含 Image 0(fdt) / Image 1(kernel) / Image 2(resource)，默认 Configuration 'conf'

# update.img 合法性与大小
ls -la output/update/Image/update.img           # ~1.1G
xxd  output/update/Image/update.img | head -1   # 52 4b 46 57 = "RKFW"
```

### 3.2 板端验证（烧录后，ssh board）
```bash
uname -a                  # 必须显示 6.1.118 且编译者 itc@itc（不是 5.10 / dzl）
zcat /proc/config.gz | grep -E "XDP_SOCKETS=|BPF_JIT=|HUGETLBFS=|DEBUG_INFO_BTF="
ls /sys/kernel/btf/vmlinux          # 应存在（BTF）
# YT6801 内置：zcat /proc/config.gz | grep YT6801
```
> 重要：`uname -a` 显示的是**实际运行内核二进制**里编死的版本，不能被“版本记录”误导。若仍显示旧版本，说明烧录未真正覆盖 boot 分区（本次 5.10 仍运行即此根因）。

## 5. 烧录（板端整包写入）

```bash
# 板子进 Loader/RockUSB（或 Maskrom）模式后，在刷机主机执行：
upgrade_tool uf /data/kkkqkx/rk3588bsp/output/update/Image/update.img
# 若在 Maskrom：先 upgrade_tool ul rk3588_spl_loader_v1.19.113.bin
```
烧完断电上电，板子即从 6.1.118 启动。**务必确认 `upgrade_tool` 回显 “Upgrade firmware ok”**——否则等于没写（本次 5.10 仍运行的根因正是烧录未生效，见 §3.2 注与下条教训）。

## 6. 烧录未生效的典型排查（本次 5.10 仍运行教训）

- `uname` 编译者署名与 `cmdline` 的 `androidboot.fwver=...uboot-日期` 是判断“是否真的刷进去了”的最快依据：若仍是旧署名/旧 uboot 日期，说明整包没写。
- 常见原因：板子**未处于正确的刷机模式**（Loader/RockUSB 或 Maskrom），`upgrade_tool` 连不上却没报错；或板子从 **SPI / 其他存储** 启动而 eMMC 未被更新。
- 板端 `lsblk` 看实际分区数与 `parameter.txt` 是否一致：本次板子 eMMC 有 9 个分区（p1–p9），而本 SDK `parameter.txt` 只有 8 个（uboot/misc/boot/recovery/backup/userdata/oem/rootfs），说明整包参数表未被应用 → 整包烧录未真正执行到该 eMMC。
