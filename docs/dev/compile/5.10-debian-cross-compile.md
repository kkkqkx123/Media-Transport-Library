## 1. 两个 app 的依赖关系（来自各自 `meson.build`）

`mtl`、`libdpdk` 不在板上（MTL 未装），由交叉构建产生后装进 `$STAGING`，经 `PKG_CONFIG_PATH` 暴露。其余为板端系统库，已随 `sysroot/` 提供。

### 1.1 `app/rk3588_end2end`（`e2e_app`）

| 依赖 | 来源 | 必需性 |
|---|---|---|
| `libdrm` | 板（sysroot） | 必需（Phase 1+） |
| `threads` (pthread) | 工具链/glibc | 必需 |
| `rockchip_mpp` | 板（BSP，`rockchip_mpp 1.3.9`） | `e2e_app` 需 `found()`，否则静默跳过 |
| `librga` | 板（BSP，`librga 2.1.0`） | 同上 |
| `mtl` | 交叉构建的 libmtl（staging） | 同上 |
| `json-c` | 板（sysroot，`json-c 0.15`） | 同上 |

`meson.build` 是分阶段 `if found()` 门控：MPP/RGA 缺失 → Phase 3 及之后全跳过；`mtl`/`json-c` 缺失 → 仅 `e2e_app` 不生成（`e2e_hal`/`e2e_io`/`test_*` 仍编）。**交叉下缺依赖会静默跳过（RB16），必须做产物断言。**

### 1.2 `app/rk3588_mp4_dist`（`mp4_dist_tx` / `mp4_dist_rx`）

| 依赖 | 来源 | 必需性 |
|---|---|---|
| `mtl` | staging | **必需**（`required: true`） |
| `libavformat`/`libavcodec`/`libavutil` (FFmpeg) | 板（sysroot，**4.4 系**，见 §9 RB15） | `build_tx`/`build_rx` 时必需 |
| `json-c` | 板（sysroot） | 同上 |
| `rockchip_mpp` | 板（BSP） | 仅 `build_rx`，且 meson 会跑 `cc.links` 链接测试（天然 sysroot 检查点） |
| `libdrm` | 板（sysroot） | 仅 `build_rx` |
| `alsa` | 板（sysroot，`alsa 1.2.4`，**新装**） | 仅 `build_rx` |
| `threads` | 工具链 | 必需 |

`build_rx=true` 时若 MPP 找不到或不链接，meson 直接 `error()` 终止（比 end2end 更严格）。

## 4. gitignore 策略（不污染 git 状态）

本地产物**整体不进 git**，避免 `git status` 被海量头文件/`.so` 污染、仓库膨胀：

- **`sysroot/`**：整个导出目录在仓库根 `.gitignore` 中忽略（`sysroot/`）。它是从板端按 §2.3 重导的**本地构建产物**，不提交；克隆后按 §2.3 重新导出即可。
- **`staging/`**：patched DPDK / libmtl / MtlManager 交叉构建的安装树（§7），同样忽略。
- **`build-*/`**：各 meson 交叉构建目录（如 `build-aarch64`），同样忽略（仓库原有 `build/` 只匹配名为 `build` 的目录）。
- 仓库全局 `.gitignore` 已覆盖 `*.so`/`*.so.*`/`*.a`/`*.o` 等二进制，作为 `sysroot/` 被忽略后的二次保险。

> 因此 `git status` 只应出现：本指南 `docs/dev/compile/`、板端分析 `docs/env/` 文档，以及 `.gitignore` 自身的改动——其余都是被忽略的本地产物。

- **绝对软链已改写为相对**（共 48 处）：无论是否提交，本地构建时都必须做，否则交叉链接器会顺着 `/usr/lib/aarch64-linux-gnu/...` 链到宿主 x86 库且不报错（RB11）。改写脚本见 §4.2。
- 克隆仓库后 `sysroot/` 不存在，需先按 §2.3 重导（含软链改写）才能本地交叉构建。

### 4.2 绝对软链改写（已执行，留存命令）

```bash
cd <repo>
python3 - <<'PY'
import os
root = "sysroot"
for dp, _, fns in os.walk(root):
    for n in fns:
        p = os.path.join(dp, n)
        if os.path.islink(p):
            t = os.readlink(p)
            if t.startswith("/"):
                tgt = os.path.normpath(os.path.join(root, t.lstrip("/")))
                rel = os.path.relpath(tgt, os.path.dirname(p))
                os.remove(p); os.symlink(rel, p)
PY
```

## 5. 宿主（x86_64）交叉工具链

实际交叉构建在**编译服务器 `devs`**（Ubuntu 18.04 x86_64，`/data/kkkqkx`）上进行，使用 **ARM 官方 GNU Toolchain 的 x86 宿主交叉编译器 `aarch64-none-linux-gnu-gcc`**（见 §5.2 / §12）。本地 WSL(Arch) 仅用于前期探测，且其 cross gcc 有 `--sysroot` 缺陷（见下），**不用于正式构建**。

### 5.1 遗留问题（已分析+修复）：Arch cross gcc 的 `--sysroot` 失效

在本地 Arch 上实测：`aarch64-linux-gnu-gcc 16.1.0` 的 `CROSS_SYSTEM_HEADER_DIR` 是**绝对路径** `/usr/aarch64-linux-gnu/include`，`--sysroot=S` **不会**把它重定位到 `S/usr/include`。结果编译时仍吃工具链自带的 glibc 2.4x 头文件，而我们导出的 Debian 板端 sysroot（`S/usr/include`，glibc 2.31）完全没被找到，导致标准头文件解析失败。

**根因**：Arch 的 cross gcc 以 `/usr/aarch64-linux-gnu` 为默认 sysroot，且其系统头目录被硬编码为绝对路径，`--sysroot` 无法 relocate。Debian/Ubuntu 的 `gcc-aarch64-linux-gnu` 则是多 arch 感知的，`--sysroot` 能正确把 `<sysroot>/usr/include` 与 `<sysroot>/usr/lib/aarch64-linux-gnu` 纳入搜索——正好是本仓库 sysroot 的布局。

**修复（采用）**：`devs` 是 x86，**SDK 自带的 `aarch64-linux-gnu-gcc-12` 实为本机 aarch64 原生二进制**（ELF ARM aarch64，解释器 `/lib/ld-linux-aarch64.so.1`），在 x86 上根本跑不起来——所以不能用它。改为在 `devs` 下载 **ARM GNU Toolchain（`aarch64-none-linux-gnu-gcc`，x86 宿主、aarch64 目标）**：它自带 gcc/crt/libgcc，配合板端 sysroot 用 `--sysroot` 精确匹配板子 glibc 2.31（见 §5.2 / §12）。本地 Arch 若想构建，退路是用 `-nostdinc` + 显式 `-isystem` 并补回 gcc 内部 include，但本任务走 devs 的 ARM Toolchain。

### 5.2 编译服务器 `devs` 工具链落地（ARM GNU Toolchain）

```bash
# 1) ARM 官方 x86 宿主交叉编译器（一次即可，约 150MB）
#    实际下载方式：devs / 本地直连 developer.arm.com 与 github 均被限速或阻断，
#    改为在**工作站用本地代理**抓取后 rsync 到 devs（仅下载走代理，ssh/rsync 不要代理）：
#      http_proxy=http://localhost:7890 https_proxy=http://localhost:7890 \
#        curl -L -C - -o arm-toolchain.tar.xz \
#        https://armkeil.blob.core.windows.net/developer/Files/downloads/gnu/13.3.rel1/binrel/arm-gnu-toolchain-13.3.rel1-x86_64-aarch64-none-linux-gnu.tar.xz
#      rsync arm-toolchain.tar.xz devs:/data/kkkqkx/        # 注意：rsync/ssh 时切勿带 http_proxy
#      ssh devs 'cd /data/kkkqkx && tar xf arm-toolchain.tar.xz'
export TOOL=/data/kkkqkx/arm-gnu-toolchain-13.3.rel1-x86_64-aarch64-none-linux-gnu
export PATH=$TOOL/bin:$PATH
aarch64-none-linux-gnu-gcc --version        # 期望 13.x

# 2) meson / ninja：优先用 SDK buildroot 宿主版；过旧则另装
export SDK=/data/kkkqkx/rk3588bsp
export PATH=$SDK/buildroot/output/rockchip_rk3588/host/bin:$PATH
meson --version; ninja --version
```

> 交叉文件名（tuple）是 `aarch64-none-linux-gnu-*`，与交叉文件 §6.1 一致。该 toolchain **非 Debian 多 arch 感知**，故交叉文件里对板端 sysroot 额外加 `-B$REPO/sysroot/usr/lib/aarch64-linux-gnu`（找 `crt1.o` 等启动对象）与 `-isystem $REPO/sysroot/usr/include/aarch64-linux-gnu`（arch 专属头）。

- `clang` 用于把 `manager/mtl.xdp.c` 编成 `mtl.xdp.o`（BPF 与目标架构无关）；`devs` 上装 `sudo apt-get install clang`（x86 clang 即可，BPF 无关架构）。
- `aarch64-none-linux-gnu-pkg-config` 不需要——交叉语义全靠宿主 `pkg-config` + 环境变量（§6）。

## 6. 交叉文件与 pkg-config 环境

### 6.1 生成 `aarch64.ini`（路径必须绝对）

```bash
cd <repo>
export REPO=$PWD
cat > sysroot/aarch64.ini <<INI   # 注意 heredoc 不引号，让 $REPO 展开成绝对路径
[binaries]
c = 'aarch64-none-linux-gnu-gcc'
cpp = 'aarch64-none-linux-gnu-g++'
ar = 'aarch64-none-linux-gnu-ar'
strip = 'aarch64-none-linux-gnu-strip'
pkg-config = 'pkg-config'
ld = 'aarch64-none-linux-gnu-ld'

[built-in options]
c_args = ['--sysroot=$REPO/sysroot',
          '-isystem$REPO/sysroot/usr/include/aarch64-linux-gnu']
cpp_args = c_args
c_link_args = ['--sysroot=$REPO/sysroot',
               '-B$REPO/sysroot/usr/lib/aarch64-linux-gnu',
               '-L$REPO/sysroot/usr/lib/aarch64-linux-gnu',
               '-L$REPO/sysroot/lib/aarch64-linux-gnu']
cpp_link_args = c_link_args

[host_machine]
system = 'linux'
cpu_family = 'aarch64'
cpu = 'armv8-a'
endian = 'little'
INI
```

> `$REPO` 必须是仓库绝对路径（meson cross file 不展开 `~`/相对路径）。unquoted heredoc 会让 `$REPO` 在本机展开；若手工编辑，请直接写死绝对路径。

### 6.2 每层构建都要导出的 pkg-config 三件套

```bash
export PKG_CONFIG_SYSROOT_DIR=$REPO/sysroot
export PKG_CONFIG_LIBDIR=$REPO/sysroot/usr/lib/pkgconfig:$REPO/sysroot/usr/share/pkgconfig:$REPO/sysroot/usr/lib/aarch64-linux-gnu/pkgconfig
export PKG_CONFIG_PATH=$STAGING/lib/pkgconfig:$STAGING/lib/aarch64-linux-gnu/pkgconfig
```

`PKG_CONFIG_LIBDIR` 必须显式覆盖，否则宿主 x86 的 `.pc`（json-c 等）会漏进来导致静默架构错配（RB12）。

## 7. 构建顺序（依赖序，全部带同一份 `aarch64.ini`）

设 `REPO=<仓库绝对路径>`、`STAGING=$REPO/staging`、`CROSS=$REPO/sysroot/aarch64.ini`。

### 7.1 patched DPDK（`libdpdk.pc`，必做）

```bash
cd $REPO
DPDK_VER=$(grep DPDK_VER versions.env | cut -d= -f2)     # 26.07
curl -LO https://fast.dpdk.org/rel/dpdk-$DPDK_VER.tar.xz
tar xf dpdk-$DPDK_VER.tar.xz
cd dpdk-$DPDK_VER
for p in $REPO/patches/dpdk/$DPDK_VER/*.patch; do patch -p1 -i "$p"; done
meson setup build-aarch64 --cross-file $CROSS \
  -Dplatform=generic -Dcpu_instruction_set=armv8-a \
  -Denable_drivers=net/null,net/af_xdp,bus/pci,bus/vdev,common/iavf \
  -Dtests=false -Dexamples= --prefix=/usr
ninja -C build-aarch64 && DESTDIR=$SYSROOT ninja -C build-aarch64 install
```
- `numa` 头/库已在 sysroot，`-Dplatform=generic` + `armv8-a` 最稳。
- 绕开 `script/build_dpdk.sh`（其版本检测用宿主 `libdpdk.pc`，交叉下不可用，RB14）。

### 7.2 xdp-tools + libbpf（仅 AF_XDP 路线，可选但推荐）

```bash
cd $REPO
XDP_VER=$(grep XDP_TOOLS_VER versions.env | cut -d= -f2)   # 1.6.3
curl -LO https://github.com/xdp-project/xdp-tools/archive/refs/tags/v$XDP_VER.zip
unzip v$XDP_VER.zip && cd xdp-tools-$XDP_VER
make CC=aarch64-none-linux-gnu-gcc ARCH=aarch64 BPF_CC=clang PREFIX=/usr
make CC=aarch64-none-linux-gnu-gcc ARCH=aarch64 BPF_CC=clang PREFIX=/usr DESTDIR=$SYSROOT install
```
- 完成后 `libxdp.pc`/`libbpf.pc` 进 `$STAGING`。
- 跳过此步则 libmtl 静默退化为无 AF_XDP 后端（RB2/RB18），但**必须断言** `MTL_HAS_XDP_BACKEND`。

### 7.3 libmtl（核心）

```bash
cd $REPO
meson setup build-aarch64 --cross-file $CROSS --prefix $STAGING \
  -Dbuildtype=release -Denable_tests=false
ninja -C build-aarch64 && ninja -C build-aarch64 install
grep -q MTL_HAS_XDP_BACKEND build-aarch64/config.h && echo "XDP backend ENABLED" || echo "XDP backend OFF"
```
- aarch64 gcc 有一套新告警集，`-Werror`（release）首次易挂（RB13）：先用 `-Dbuildtype=debugonly` 收集告警修完再回 release。
- SIMD 探测自然退化（`st_avx2/avx512` 编译为空单元），无需处理（文档 01 §3.2）。

### 7.4 MtlManager（AF_XDP 路线必做）

```bash
cd $REPO/manager
meson setup build-aarch64 --cross-file $CROSS --prefix $STAGING
ninja -C build-aarch64 && ninja -C build-aarch64 install
# 产物含 <staging>/lib/bpf/mtl.xdp.o（clang 编的 BPF，架构无关）
```

### 7.5 两个 rk3588 应用（真正交付物）

```bash
# end2end
cd $REPO/app/rk3588_end2end
meson setup build-aarch64 --cross-file $CROSS
ninja -C build-aarch64
test -x build-aarch64/e2e_app && echo "e2e_app built" || echo "e2e_app SKIPPED (依赖缺失)"

# mp4_dist（tx+rx）
cd $REPO/app/rk3588_mp4_dist
meson setup build-aarch64 --cross-file $CROSS -Dbuild_tx=true -Dbuild_rx=true
ninja -C build-aarch64
test -x build-aarch64/mp4_dist_tx && echo "mp4_dist_tx built"
test -x build-aarch64/mp4_dist_rx && echo "mp4_dist_rx built"
```

依赖解析全部走 §6.2 的 pkg-config 环境：`mtl`/`libdpdk` 来自 `$STAGING`，板端库来自 `sysroot`。`mp4_dist` 的 `build_rx` 会实跑 MPP 链接测试（交叉 gcc + sysroot），是验证 MPP 进 sysroot 的天然检查点（RB16）。

## 12. 在编译服务器 `devs` 上构建（环境 + setsid 启动 + 轮询）

`devs`：`Ubuntu 18.04 x86_64`，项目位于 `/data/kkkqkx/mtl`。后台构建与轮询套路参考 `docs/dev/RK3588_6.1_KERNEL_FULL_BUILD.md` §2.1（`setsid` 脱离会话 + 循环心跳，避免 ssh 断开杀进程）。

### 12.1 一次性环境

```bash
export REPO=/data/kkkqkx/mtl
export SDK=/data/kkkqkx/rk3588bsp
export TOOL=/data/kkkqkx/arm-gnu-toolchain-13.3.rel1-x86_64-aarch64-none-linux-gnu
export PATH=$TOOL/bin:$SDK/buildroot/output/rockchip_rk3588/host/bin:$PATH
export STAGING=$REPO/staging
# 生成 cross file（§6.1），并导出 pkg-config 三件套（§6.2）
cd $REPO && export REPO=$PWD
# …按 §6.1 / §6.2 设置 PKG_CONFIG_SYSROOT_DIR / LIBDIR / PATH…
```

> 若 buildroot 的 `meson` 版本过低跑不动 DPDK 26.07，换用新 meson：在 `devs` 上 `python3 -m pip` 不可用（无 pip），可改用 SDK 内其他 buildroot host 的 meson，或 `sudo apt-get install python3-pip` 后 `pip3 install 'meson>=1.0' ninja` 并用该 meson 的 python 解释器（需 python≥3.7）。

### 12.2 后台启动 + 轮询（推荐）

把 §7 的整段构建写成一个 `build_aarch64.sh`（`set -e`，全程 `>> build_aarch64.log 2>&1`），然后：

```bash
cd $REPO
setsid bash -c "bash build_aarch64.sh > build_aarch64.log 2>&1" < /dev/null &

# 轮询：每 60s 心跳；进程退出或产物出现即止
for i in $(seq 1 400); do
  sleep 60
  echo "[$(date +%H:%M:%S)] tick $i"; tail -3 build_aarch64.log
  [ -x $REPO/app/rk3588_mp4_dist/build-aarch64/mp4_dist_rx ] && { echo APPS_DONE; break; }
  pgrep -f build_aarch64.sh >/dev/null || { echo BUILD_PROC_GONE; tail -40 build_aarch64.log; break; }
done
```

> 远端 `sleep` 期间无输出会触发 idle 超时，轮询循环里用 `echo`/心跳即可避免；本次沿用 6.1 文档实证有效的做法。

### 12.3 构建脚本骨架（参考）

```bash
#!/usr/bin/env bash
set -e
REPO=/data/kkkqkx/mtl; SDK=/data/kkkqkx/rk3588bsp
export TOOL=/data/kkkqkx/arm-gnu-toolchain-13.3.rel1-x86_64-aarch64-none-linux-gnu
export PATH=$TOOL/bin:$SDK/buildroot/output/rockchip_rk3588/host/bin:$PATH
export PKG_CONFIG_SYSROOT_DIR=$REPO/sysroot
export PKG_CONFIG_LIBDIR=$REPO/sysroot/usr/lib/pkgconfig:$REPO/sysroot/usr/share/pkgconfig:$REPO/sysroot/usr/lib/aarch64-linux-gnu/pkgconfig
export STAGING=$REPO/staging; CROSS=$REPO/sysroot/aarch64.ini
# 7.1 DPDK → 7.2 xdp-tools → 7.3 libmtl → 7.4 MtlManager → 7.5 apps
# （命令见 §7，逐层 ninja 后断言产物）
echo "=== DPDK ===";   (cd $REPO/dpdk-26.07   && meson setup build-aarch64 --cross-file $CROSS ... && ninja -C build-aarch64 && DESTDIR=$STAGING ninja -C build-aarch64 install)
echo "=== libmtl ==="; (cd $REPO && meson setup build-aarch64 --cross-file $CROSS --prefix $STAGING && ninja -C build-aarch64 && ninja -C build-aarch64 install)
grep -q MTL_HAS_XDP_BACKEND $REPO/build-aarch64/config.h && echo "XDP backend ENABLED" || echo "XDP backend OFF"
echo "=== apps ===";   (cd $REPO/app/rk3588_end2end && meson setup build-aarch64 --cross-file $CROSS && ninja -C build-aarch64)
echo ALL_DONE
```
