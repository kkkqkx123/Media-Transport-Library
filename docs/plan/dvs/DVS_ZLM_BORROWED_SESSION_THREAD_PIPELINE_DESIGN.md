# 借鉴 ZLMediaKit 的三点增量设计：会话注册视图、线程收敛、管线分层对齐

> 输入：`docs/archive/dvs_agent_media_role_decision.md`、
> > `docs/plan/dvs/DVS_AGENT_MEDIA_IPC_FOLLOWUP_ANALYSIS.md`。
> 约束：只改原模块，不起替代性新模块；不做兼容层；版本保持为 `1`；
> 设计只用自然语言描述，不贴完整代码。

## 1. 目标与非目标

目标是把 ZLMediaKit 中真正适配本节点的三点思想落地为可实施的增量：
会话统一视图、控制面任务边界与线程可观测性、收发管线职责对齐。

非目标：不合并代理与媒体进程，不引入 EventPoller 或外部线程池库，
不新增通用协议栈与软件编解码，不改变现有 Unix socket 行协议与平台契约，
不提前做包络统一与订阅模型（见 IPC 后续分析的排序，包络稳定之后再做）。

## 2. 设计一：会话统一注册视图（对应 MediaSource 思想）

现状是会话信息散在三处：准入模块持有白名单加定长 LRU 映射，
引擎持有运行计数与音频路由，通道就绪与丢包来自合成器的通道统计，
状态查询在 IPC 桥接里临时拼装。三处口径不一致时，屏障核对与排障只能靠日志对齐。

设计是在现有模块内收敛出一个只读的统一会话视图，职责不变：

- 准入模块继续是唯一的准入判决点，白名单语义与 LRU 驱逐语义不动，
  只增加快照能力的完备性，使调用方一次拿到全部活跃会话的标识与通道号。
- 会话管理模块继续是引擎生命周期的拥有者，负责把基础配置、布局应用、
  停止请求串起来，不新增会话存储，只在现有布局提交与清理路径上同步视图。
- 引擎编排模块继续持有 MTL 实例与合成器指针以及收发互斥，
  布局提交仍走重建合成器的现实路径，视图只读其结果，不反向驱动重建时机。
- 状态查询路径继续由 IPC 桥接拼装，改为从上述三处按固定顺序取数后合并，
  排序为先会话标识、再通道就绪、再音视频计数，任一来源缺失时按空集处理，
  不阻塞、不重试、不缓存旧值。

验收以行为为准：同一布局下连续查询的会话集合单调一致；
通道数变化只发生在提交成功之后；查询慢不影响布局下发时延。

## 3. 设计二：控制面任务边界与线程可观测性（对应 TaskExecutor 思想）

现状是读线程既收发又执行提交与清理，耗时准备虽已走独立工作线程，
但提交仍在读线程上同步重建合成器，一次慢提交会拖住同一连接的后续请求；
线程亲和已有配置项但命名缺失，联调时只能靠线程号猜测归属。

设计分两步，均在原模块内部：

- IPC 服务端增加一个有界的单工作队列承载提交与清理重操作，
  读线程只做行协议解析、幂等重放判断与入队。
  队列深度取小值，满时直接回压并返回可重试的忙状态，不堆积、不丢弃、不另起线程。
  准备路径保持现状的按请求工作线程不变，待提交队列稳定后再考虑是否合流，
  避免一次改动两个并发结构。
- 线程命名与亲和收敛：解码线程、渲染线程、编码线程、监管线程、
  桥接线程、引擎统计线程、IPC 工作线程在创建后统一命名，
  命名只含角色与通道号，不含文档编号等外部引用。
  亲和策略不动，仍由现有采集、编码、桥接、解码、渲染、音频配置项驱动，
  缺省值为负即不绑定，保证 x86 无硬件构建的行为不变。

验收以行为为准：慢提交期间查询仍可返回；队列满时客户端收到明确忙信号；
单板上按线程名可直接区分解码、渲染、编码、桥接归属。

## 4. 设计三：管线分层对齐（对应 HdmiIn 分层思想）

ZL 的 HdmiIn 按采集、转换、编码、媒体源、协调器分层，本节点收发管线已同构，
无需重建。现状分工是：采集、格式转换、编码、发送封装留在发送 donor，
解码、合成、显示、音频仲裁留在接收 donor 与共享目录，
媒体引擎只做角色互斥、参数校验、状态机、布局执行与能力上报，
发送数据面通过后端钩子由引擎编排而非由引擎实现。

设计是守住该分工，只补齐三处缝隙：

- 发送后端上下文继续由引擎在 MTL 就绪后下发，采集与编码线程归属仍在 donor 管线内，
  引擎不直接创建数据面线程，只持有启停手柄并保证启停与角色切换对称。
- 采集端口映射与能力探测继续共用同一套物理身份扫描，
  启动前重扫并拒绝无信号目标的语义不变，避免两处扫描口径分叉。
- 布局执行继续是输出角色的唯一画面决策点，几何变更走快速路径，
  其余变更走重建路径，音频仲裁结果随布局提交生效，不单独开音频通道。

验收以行为为准：输入角色只跑发送链、输出角色只跑合成链，角色切换后对端链路必停；
donor 源码仍由引擎 in-tree 编译直接复用，不出现拷贝副本。

## 5. 实施顺序与回归面

先做设计二中的线程命名（无行为变更，可独立合入），
再做设计一的视图收敛（只改查询拼装顺序，不改准入语义），
再做设计二中的有界工作队列（改并发结构，需配合 IPC 压测），
最后做设计三的缝隙补齐（需单板冒烟）。

回归面：IPC 现有自测覆盖状态机与幂等重放，工作队列合入后需加压测用例；
会话视图合入后需核对状态查询快照；
管线改动需跑发送与接收 donor 的原有测试，外加单板收发互通。
任一步若与代码矛盾，以代码为准并回写本文。
