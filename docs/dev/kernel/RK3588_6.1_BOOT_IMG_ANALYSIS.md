# RK3588 6.1 内核 boot.img 产物分析与可烧录性

分析对象：devs `/data/kkkqkx/rk3588bsp` 上按 `docs/dev/compile/RK3588_6.1_KERNEL_BUILD.md`
流程编译产出的 `kernel-6.1/boot.img`（软链 `output/firmware/boot.img`）。编译日期 2026-10-26，
对应 SDK 提交 `98e7f9606`（AF_XDP/eBPF）+ `6b4e691d6`（构建修复：关闭 `CONFIG_STMMAC_UIO`）。

## 1. 结论速览

- `boot.img` 是标准 Rockchip **FIT（Flattened Image Tree）** 镜像，内部打包了**未压缩内核
  Image + 板级 DTB + resource 镜像**三块。它本身是「内核分区镜像」，不是「整盘烧录镜像」。
- 本次所有源码/配置/固件改动**都已烘焙进 `boot.img` 的 Image**（Mali 固件因 `CONFIG_MALI_VALHALL=y`
  内置且被 `.incbin` 编入内核，也在其中）。主机的 `pahole`/`libelf-dev` 等只是构建期依赖，不进镜像。
- **能否直接烧录**分两种场景：
  - **仅更新内核**（板上其余分区 MiniLoader/uboot/trust/rootfs 已存在且同源）：可以，把 `boot.img`
    烧到 `boot` 分区即可（rkdeveloptool / upgrade_tool / fastboot）。
  - **整板全新烧录**：不可以单独用 `boot.img`，需要 `./build.sh updateimg` 生成的 `update.img` 整包。

## 2. 构建产物清单

| 产物 | 路径 | 大小 | 说明 |
|---|---|---|---|
| `boot.img` | `kernel-6.1/boot.img` → `output/firmware/boot.img` | 56,111,616 B | FIT 内核镜像（含 Image+DTB+resource） |
| `Image` | `kernel-6.1/arch/arm64/boot/Image` | 55,452,160 B | 未压缩 ARM64 内核，即 FIT 内的 kernel 块 |
| `ztl-rk3588-cm.dtb` | `kernel-6.1/arch/arm64/boot/dts/rockchip/ztl-rk3588-cm.dtb` | 308,835 B | 板级设备树（DTB v17），即 FIT 内的 fdt 块 |
| `resource.img`（内含） | 编入 boot.img FIT 的 resource 块 | 347,136 B | uboot 阶段用的 DTB/logo 等，即 FIT 内的 resource 块 |

> `file boot.img` 显示 `Device Tree Blob version 17, size=1536`，那是 FIT 外层头（ITS 编译出的
> 小 DTB 头）；真正的镜像内容要用 `rkbin/tools/mkimage -l boot.img` 看（见 §3）。

## 3. boot.img 的 FIT 内容（`rkbin/tools/mkimage -l` 实测）

```
FIT description: U-Boot FIT source file for arm
Created:         Mon Oct 26 01:33:52 2026
 Image 0 (fdt)        Flat Device Tree   308835 B   AArch64  Load 0xffffff00
 Image 1 (kernel)     Kernel Image       55452160 B AArch64 Linux  uncompressed  Load/Entry 0xffffff01
 Image 2 (resource)   Multi-File Image   347136 B   uncompressed
 Default Configuration: 'conf'  ->  Kernel: kernel, FDT: fdt
```

即 `boot.img = FIT{uImage}` 把 **内核 Image（52.88 MiB）+ 板级 DTB（301 KiB）+ resource 镜像
（339 KiB）** 打成一个包，默认配置 `conf` 用 kernel+dtb 引导。这是 Rockchip 6.1 SDK 的标准 boot FIT
（`RK_USE_FIT_IMG=y` + `boot.its`）。`%.img` 阶段先产 `Image.lz4`，FIT 阶段再用未压缩 `Image`
覆盖，故 FIT 内 kernel 为未压缩原 Image。

## 4. 本次所有修改是否都进了 boot.img

| 修改项 | 来源 | 是否进 boot.img | 说明 |
|---|---|---|---|
| AF_XDP/eBPF 使能（`ztl_defconfig`/`ztl_rk3588.config`/`ztl-rk3588-cm.dts`/`Config.in.kernel`） | 提交 `98e7f9606` | 是 | 全部编译进 Image 与 DTB |
| 关闭 `CONFIG_STMMAC_UIO` | 提交 `6b4e691d6` | 是 | 该驱动不再编译进内核 |
| Mali CSF 固件 `mali_csffw.bin` | 编译前手动复制（gitignored） | 是 | `CONFIG_MALI_VALHALL=y` 内置，固件被 `.incbin` 链入 Image |
| 主机 `pahole`(dwarves) / `libelf-dev` | apt 安装 | 否（无需进镜像） | 纯构建期依赖，只影响编译能否通过 |

**结论**：所有影响运行期内核的源码/配置/固件改动都已烘焙进 `boot.img` 的 `Image`；主机构建工具
不影响镜像内容。`boot.img` 自包含地携带了 Mali 固件（因驱动内置），无需板上另放固件文件。

§4 验证（编译后实测）确认关键项全部 `=y`：
`XDP_SOCKETS`/`XDP_SOCKETS_DIAG`、`BPF_SYSCALL`、`BPF_JIT`/`BPF_JIT_ALWAYS_ON`/
`BPF_UNPRIV_DEFAULT_OFF`、`CGROUP_BPF`、`HUGETLBFS`、`DEBUG_INFO_BTF`/`DEBUG_INFO_BTF_MODULES`、
`CONFIG_YT6801=y`。

## 5. 能否直接用于烧录

### 5.1 仅更新内核（推荐日常迭代）
板上已烧好完整固件、仅需换内核时，`boot.img` 可直接烧到 `boot` 分区：

```bash
# 方式 A：进入板端 uboot 的 rockusb/maskrom 模式后用 rkdeveloptool（按分区名）
rkdeveloptool ul rk3588_spl_loader_v1.xxx.bin      # 先下载 MiniLoader（maskrom 时）
rkdeveloptool di -b boot ./kernel-6.1/boot.img     # 按分区名写入 boot
# 或升级模式（loader 已起）用 upgrade_tool
upgrade_tool di -b boot ./kernel-6.1/boot.img
# 方式 B：板端进 fastboot（uboot 命令行执行 fastboot usb 0）
fastboot flash boot ./kernel-6.1/boot.img
fastboot reboot
```

前提：MiniLoader / uboot / trust / rootfs 等其余分区已存在且与本次 SDK 基线同源（cm588 板级无自定义
`RK_PARAMETER`，用 `device/rockchip/.chips/rk3588/parameter.txt` 默认分区表，`boot` 分区名固定）。
`boot.img` 为标准 FIT，uboot 能直接引导其中的未压缩 ARM64 Image，**无需先烧整包**。

### 5.2 整板全新烧录
**不能**单独用 `boot.img`。需要 `./build.sh updateimg` 生成的 `output/firmware/update.img` 整包
（打包 boot.img + MiniLoaderAll.bin + uboot + trust + rootfs + misc/recovery 等），用
rkdeveloptool / AndroidTool 全盘写入。流程：

```bash
cd /data/kkkqkx/rk3588bsp
./build.sh firmware      # 汇总/校验 output/firmware 下各镜像
./build.sh updateimg     # afptool+rkImageMaker 生成 output/firmware/update.img
```

## 6. boot.img 不含、但运行期需要的东西（MTL / AF_XDP 落地）

`boot.img` 只解决「内核本身具备 XDP/BPF/BTF/大页能力」。要让 MTL `native_af_xdp` 后端真正跑起来，
板上还需：

- **用户态 MTL 库与 rk3588 应用**：需交叉编译（见 `docs/dev/02-x86到RK3588交叉编译分析.md`），
  不在内核镜像里。
- **大页运行期分配**：内核已开 `HUGETLBFS`，但需运行时分配（内核 cmdline `hugepagesz=2M
  hugepages=N` 或 `mount -t hugetlbfs` 后写 `/sys/kernel/mm/hugepages/.../nr_hugepages`）。
- **MtlManager / 端口名**：启动 `MtlManager` 仲裁 lcore/队列；AF_XDP 走 `yt6801` 端口，板上仍只
  能 generic XDP + copy 模式（运行期限制，与编译无关）。
- **运行期校验**（烧录后）：
  ```bash
  zcat /proc/config.gz | grep -E "XDP_SOCKETS|BPF_JIT|HUGETLBFS|DEBUG_INFO_BTF"   # 若开 IKCONFIG
  ls /sys/kernel/btf/vmlinux            # BTF 生成成功
  ```
