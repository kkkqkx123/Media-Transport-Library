# DVS 节点内 IPC 后续改进项分析

> 范围：只收录上一轮（`DVS_AGENT_MEDIA_IPC_ISSUES_AND_FIX_PLAN.md`，已合入）有意后移的事项，以及当时为控制变更面而未动的深层问题。不动平台通道（见 `DVS_WS_CHANNEL_ISSUES_AND_FOLLOWUP_PLAN.md`），不动媒体数据面。
> 与 `DVS_WINDOWS_LAYOUT_MAPPING_PLAN.md` 的分工：窗体到流的翻译决策、字段增补、坐标换算、实施顺序已在该文档冻结，本篇不再重复，只在涉及处引用其结论。
> 写作约束：只用自然语言分析与方向建议，不贴完整代码；将来改动仍只做原模块内增量，不起替代性新模块；版本保持为 `1`，不做兼容层。

## 1. 总览与排序建议

上一轮闭环的是悬挂与正确性（两阶段走完、提交顺序、生效时间传递、广播隔离、套接字权限、心跳单查询）。剩下的都是重要但不紧急、且改动面更大的事项，大致分三层：先做风险收敛（鉴权与版本门禁），再做语义收敛（包络与一致性模型），最后做体验优化（订阅模型与可观测）。任何一项都不应与窗体翻译的实施抢同一窗口，翻译先行，因为它是画面能否真实切换的唯一路径。

## 2. 逐项分析

### 对端鉴权缺失

现状是平台到代理有令牌防线，代理到媒体没有任何对端校验，套接字权限收紧后只能防跨用户，不能防同用户下的任意进程。高危动词（清屏、启停推流、提交布局）对本机同用户全开。风险是提权面不对等：最强的一段链路恰恰是最弱的一环。候选方向是在媒体 accept 后取对端凭据并与期望身份比对，失败即断开并记审计；代理侧无需新增配置，沿用同用户部署假设，只需保证 supervision 下两进程同属同一管控单元。该项建议排在后续第一位，因为它是纯加固、不改变任何成功路径语义，回归成本最低。

### 版本握手只告警不阻断

现状是启动时核对包版本与协议版本，失配只打印告警继续运行。保留告警的原因是启动顺序不确定：引擎可能晚于代理启动，硬拒绝会导致代理在引擎就绪前反复退出。风险是版本漂移被长期掩盖，排障时才发现两端说的不是同一种协议。候选方向是把一次性握手改为持续门禁：启动时告警、就绪前轮询核对、失配期间拒绝下发布局但保持心跳与查询可用，并把核对结果暴露在版本查询接口的配对状态里。这样既不引入启动时序依赖，又让失配从日志变成可见状态。该项与鉴权同属风险收敛层，可并行实施。

### 包络双轨

现状是对外平台契约与对内媒体协议各用一套命名与嵌套规则，准备结果事件的请求标识放在数据区而非包络，客户端须特判。风险是每新增一个动词或事件就要写两套解析，测试也要覆盖两套形状，长期维护成本翻倍。候选方向是收敛到一套：媒体协议沿用平台契约的字段名与嵌套位置，事件补齐包络；存量两套并存期间以契约为准做单向适配，收敛完成后再删旧分支。该项之所以后移，是因为它触及所有调用方与全部测试，属于破坏性变更，必须等窗体翻译落地、链路行为冻结后再做，否则翻译与包络两个变量同时在动，联调无法定界。

### 一致性模型双轨

现状是即时生效类直写、两阶段类走状态机，修订号与过期保护只存在于后者。输出口配置走后台线程加修订号比对，输入启停走同步调用，布局走事件轮询，三种异步风格并存。风险是调用方要为每个动词记一套语义，新增动词时容易选错模型。候选方向是统一为两种：凡是影响画面的走两阶段，凡是只影响本机配置的走直写加修订号；后台线程的修订号比对逻辑收敛为一处公共判定，而不是每个分支各写一次。该项同样依赖链路冻结，建议与包络统一放在同一轮，但分两次合入，先统一判定、再统一包络，避免单次变更过大。

### 单连接队头阻塞与轮询订阅

现状是代理到媒体只有一条常连接加一把大锁，全部 HTTP 处理线程与后台上报线程串行争用；事件靠轮询事件环（上百毫秒间隔、最长数秒），环满静默丢弃，还可能被其他 drain 抢走。上一轮已把最坏的持锁广播改掉，心跳也合并为单查询，但结构性问题还在：一次慢查询会拖住所有布局下发，一次事件丢失会被误判为阻塞。候选方向是分两步：先把查询与命令分离为读写两条逻辑通道（仍可复用同一套接字，用请求标识多路复用加按请求等待，而不是全局串行）；再把轮询改为等待唤醒式订阅（有事件即推，无事件即眠），轮询只保留为兜底。该项属于体验优化层，建议在鉴权、包络之后做，因为它改的是客户端并发结构，需要包络先稳定，否则等待匹配逻辑要写两遍。

### 就绪语义与模拟等待

现状是媒体准备线程固定等待一段短时间后即报就绪，与真实收流就绪无关；准备结果里的通道信息在窗体形态下为空，调用方只能把接纳当成就绪。风险是屏障收集到的全是虚假就绪，跨节点同屏的时刻精度建立在不可靠的输入上。候选方向是把就绪条件接到真实的会话准入与首帧状态上，超时仍报阻塞；窗体翻译落地后，准备结果应携带翻译后的通道摘要，使平台能按通道核对而不仅按节点计数。该项与窗体翻译强相关，建议作为翻译方案的收尾验收标准，而不是独立立项。

### 健康监督与可观测

现状是代理启动时拉一次能力，失败保旧值；引擎崩溃后代理靠下一次调用失败才感知，无主动探活与退避重连；能力漂移无告警。风险是静默降级：引擎不在了，代理看到的全是旧快照。候选方向是增加轻量探活（复用现有查询状态，失败计数连续超限即标记引擎失联并记审计），重连用退避而非忙轮询，能力合并时记录来源时间，超期未刷新即在能力查询里显式标注过期而不是静默沿用。该项改动小而独立，可插在任意两轮之间，建议尽早做，因为它是其他几项联调时的排障基础。

## 3. 建议顺序

先做健康监督（排障基础，与其他项无耦合），再做鉴权与版本门禁（风险收敛），接着等窗体翻译落地并把就绪语义作为其验收标准，然后做一致性判定统一与包络统一（语义收敛，需链路冻结），最后做通道分离与订阅模型（体验优化，依赖包络稳定）。

## 4. 非目标

本篇不涉及平台通道选型、不涉及数据面、不涉及窗体翻译细节（见映射方案文档）、不引入新的进程间传输机制。所有候选项默认沿用现有套接字与行协议，只在必要时才讨论是否需要新的同步原语，且即使引入也只放在原模块内部。
