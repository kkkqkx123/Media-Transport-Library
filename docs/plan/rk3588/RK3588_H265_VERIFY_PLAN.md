# RK3588 H265 验证方案

执行地点全部在板端与 devs 编译服务器；本地只改代码与文档，不编译不跑二进制。
本方案是 `RK3588_H265_TASKS.md` 第 2 节的展开，设计依据见 `RK3588_H265_SUPPORT_DESIGN.md`。

## 前置条件

板端具备 MtlManager、HDMI 输入信号与显示器、ffmpeg（含 libx264 与 libx265）、
`mpi_dec_test`、`ffprobe`；三个应用已按仓库交叉编译文档在 devs 构建并同步到板端。
HEVC 片源尚未生成时，先用片源脚本产出 H264 与 HEVC 两版固定片源。

## 阶段 0：构建与单测

在 devs 做 RK3588 交叉构建，输出目录用 `build-aarch64/`，三个应用均通过。
随后在板端跑随包单测，新增的接收编码配置单测与既有单测（pacing、media_clk、
drm_mode、display_layout）全绿；未知编码拒绝的用例包含在内。

TX 编码冒烟在板端直接跑编码测试的两种编码，各产出一个裸码流文件，
随后用码流分类脚本分别断言为 h264 与 hevc，且关键帧存在。
这一步同时证明 MPP 侧两种编码初始化正常。

## 阶段 1：H264 回归

不带编码变量跑正式验证脚本与单板 PlanA 脚本，行为与改动前一致：
收流等速、零丢包、零坏帧、解码无反压，渲染占比符合 latest 帧策略预期。
日志门禁脚本不加编码期望时输出与历史一致；PTS 索引零值比例为零。

## 阶段 2：H265 实时链路

设置编码变量为 h265 后重跑正式验证脚本。脚本会自动把编码透传给
发送与接收两端，并在日志中分别断言发送侧编码器与接收侧解码器均工作在
H265 上，不一致直接失败。单板 PlanA 脚本同样跟随编码切换转储后缀、
回放方式与码流分类检查。

判定：解码数与收包数比值达标、SEI 时间戳可用（PTS 索引检查通过）、
转储码流被分类为 hevc 且含参数集与 IRAP 关键帧。

## 阶段 3：H265 文件源链路

发送侧以文件源模式推送 HEVC 片源（编码来自容器本身，发送侧无需编码选项），
接收侧以 H265 配置接收。覆盖单流管线与合成器两种接收形态。
随后用抓包回放脚本对转储做离线复核：码流分类强制检查加 ffmpeg 原生解码回放，
回放产帧率达到门限。

## 阶段 4：人工核查

显示器旁按人工看屏脚本的检查单逐项确认并留痕：画面内容正确、无黑场花屏撕裂、
多窗口位置正确；有声场景确认扬声器出声连续。非交互环境只跑流取证，
标记未见证，不伪造人工结论。

## 判定与记录

每个阶段按通过或失败记录：阶段 0 看单测汇总；阶段 1 看回归脚本总判定；
阶段 2 与阶段 3 看脚本总判定加码流分类与回放产帧率；阶段 4 看见证文件结论。
任一阶段失败时保留完整日志、转储码流与索引文件再报问题，不跳阶段继续。
