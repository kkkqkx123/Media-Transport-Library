# x86 开发机 → RK3588 (aarch64) 交叉编译方案分析

本文在 `docs/dev/01-MTL编译体系分析.md`（下称“文档 01”）的基础上，分析如何在一台 x86_64 开发机上交叉编译出可在 RK3588（aarch64）上运行的 MTL 全栈：`libmtl`、patched DPDK、（可选）xdp-tools/libbpf、`MtlManager`、`RxTxApp`，以及两个 rk3588 参考应用 `e2e_app` / `mp4_dist_{tx,rx}`。

## 0. 一句话结论

可行，但仓库**没有任何现成的交叉编译支持**（无 cross file、`build.sh` 全程不传 cross 参数、`build_dpdk.sh` / `build_ebpf_xdp.sh` 均假设本机编译），因此正确做法是：**绕开 `build.sh`，手工按依赖顺序执行每一层 meson，每层都带同一个 aarch64 cross file**；板端专属依赖（MPP、RGA、内核 UAPI 头、板上的 FFmpeg/ALSA/DRM 版本）通过**从开发板导出的 sysroot** 提供，通用依赖（json-c、numa、libpcap 等）优先用 Ubuntu/Debian multiarch 的 arm64 包补进同一 sysroot。最大的工程量不在 MTL 本身，而在 **sysroot 的组装与 DPDK 的交叉构建**。

## 1. 为什么不能直接用 `build.sh`

| 障碍 | 位置 | 说明 |
| --- | --- | --- |
| 无 cross file 机制 | `build.sh` | `meson setup build …` 未带 `--cross-file`，也没留任何注入点；环境变量开关（§1.2 文档 01）里没有工具链项 |
| DPDK 脚本本机构建 | `script/build_dpdk.sh` | `meson build`（DPDK 自身目录）不带 cross file；其“已安装版本检测”用 `pkg-config libdpdk`，交叉环境下宿主机的 x86 `libdpdk.pc` 会污染判断 |
| xdp-tools 脚本本机构建 | `script/build_ebpf_xdp.sh` | 内部用 `cc -dumpmachine` 探测架构（`build_ebpf_xdp.sh:139`），本机得到 x86_64，产物是宿主架构 |
| MtlManager 的 BPF 编译 | `manager/meson.build` | 找到 libxdp+libbpf 时强制要求 `clang` + `llvm-strip`。BPF 目标本身架构无关（不需要 aarch64 clang target），但链接 `mtl.xdp.o` 进管理进程的 libbpf 调用要走 sysroot 的 libbpf 头 |
| 单测无法执行 | `./build.sh unit` | 交叉编译出的 `UnitTest` 是 aarch64 二进制，x86 上不能跑（除非配 qemu-user）。`build.sh unit` 模式“构建并直接运行后退出”，交叉场景必须只构建不运行 |

结论：交叉编译是**逐层手工 meson**，`build.sh` 只能当作“每层该做什么”的操作清单参考（文档 01 §1.2），不能直接执行。

## 2. 总体布局

在开发机上建一个独立工作区（下称 `$WS`），四棵树分工：

```
$WS/
├── toolchain/              # 交叉工具链（apt 安装即可，无需 Linaro 独立包）
├── sysroot/                # aarch64 的头文件 + 库（核心工作）
│   ├── usr/include/
│   ├── usr/lib/aarch64-linux-gnu/
│   └── lib/aarch64-linux-gnu/
├── aarch64.ini             # meson cross file（MTL / app 层共用）
└── src/
    ├── dpdk-26.07/         # patched DPDK 源码（按文档 01 §2 流程取补丁）
    ├── xdp-tools-1.6.3/    # 仅 AF_XDP 路线
    └── Media-Transport-Library/
```

最终产物统一安装进 `$WS/staging`（相当于板上的 `/usr/local`，= `MTL_INSTALL_PREFIX` 的交叉版），部署时整棵 rsync 到板子。

### 2.1 meson cross file（`$WS/aarch64.ini`）

```ini
[binaries]
c = 'aarch64-linux-gnu-gcc'
cpp = 'aarch64-linux-gnu-g++'      # 仅 MtlManager(C++17) 与 gtest 需要
ar = 'aarch64-linux-gnu-ar'
strip = 'aarch64-linux-gnu-strip'
pkg-config = 'pkg-config'          # 关键：用宿主 pkg-config，靠 env 指向 sysroot
# 注意：不要在这里写 llvm-config/clang，BPF 编译由 manager 层自己找

[built-in options]
c_args = ['--sysroot=/home/you/ws/sysroot',
          '-I/home/you/ws/sysroot/usr/include/aarch64-linux-gnu']
cpp_args = c_args
c_link_args = ['--sysroot=/home/you/ws/sysroot',
               '-L/home/you/ws/sysroot/usr/lib/aarch64-linux-gnu',
               '-L/home/you/ws/sysroot/lib/aarch64-linux-gnu']
cpp_link_args = c_link_args

[host_machine]
system = 'linux'
cpu_family = 'aarch64'
cpu = 'rk3588'          # Cortex-A76×4 + A55×4, ARMv8.2-A
endian = 'little'
```

说明：

- `pkg-config` 保持宿主的 `pkg-config` 二进制，交叉语义完全由环境变量 `PKG_CONFIG_SYSROOT_DIR` / `PKG_CONFIG_LIBDIR` / `PKG_CONFIG_PATH` 控制（§3.4），这是 meson 官方推荐的交叉方式；
- `--sysroot` 必须用**绝对路径**，meson cross file 不展开 `~` 和相对路径；
- DPDK 与 xdp-tools 不是 meson 之外的独立体系——DPDK 本身就是 meson 工程，**复用同一份 cross file**；xdp-tools 是 GNU make 体系，走各自的交叉变量（§4.2）。

## 3. sysroot：需要从开发板获取什么

sysroot 组装是整个方案里最繁琐、最容易踩坑的一步。原则：**“板上跑的每一个 `.so`，交叉链接时都要能找到同版本的 `.so` 和头文件”**。

### 3.1 必须来自开发板的（BSP 专属，multiarch 仓库没有）

| 内容 | 板上路径（典型） | 用途 |
| --- | --- | --- |
| Rockchip MPP 头 + `librockchip-mpp.so` | `/usr/include/rockchip/`、`/usr/lib/aarch64-linux-gnu/librockchip-mpp*` | `rockchip_mpp` pkg-config（end2end P3/P4、mp4_dist RX 解码） |
| RGA 头 + `librga.so` | `/usr/include/rga.h`（或 `im2d.h`）、`librga.so` | `librga` pkg-config |
| 板上 FFmpeg 7.0（若板上有自编译版） | `/usr/local/{include,lib}` | `libavformat/avcodec/avutil`。**注意**：Ubuntu 22.04/24.04 的 arm64 发行版 FFmpeg 是 4.4/6.x，与 versions.env 钉的 7.0 不一致；若接受发行版版本需同步改 `mp4_dist` 的版本假设，若必须 7.0 则在 x86 上用 `--enable-cross-compile` 自编（§4.4） |
| 内核 UAPI 头（V4L2、DRM 用户接口） | `/usr/include/linux/`、`/usr/include/linux/videodev2.h` 等 | 来自板上的 `linux-libc-dev` 或 BSP 内核头包；**用板上版本而不是宿主机的 x86 linux-libc-dev**，保证 V4L2 接口定义与板内核一致 |
| `libasound.so.2` + alsa 头 | `/usr/include/alsa/` | `alsa` pkg-config（mp4_dist RX 音频） |

导出方式（在板上执行，回传到 `$WS/sysroot`）：

```bash
# 板上：打包根文件系统里的头与库（不拷整个 rootfs）
sudo tar czf /tmp/rk3588_sysroot.tar.gz \
  /usr/include \
  /usr/lib/aarch64-linux-gnu \
  /usr/lib/pkgconfig /usr/share/pkgconfig \
  /lib/aarch64-linux-gnu \
  /usr/local/include /usr/local/lib
# 开发机：解到 sysroot/，并把绝对符号链接改写为 sysroot 内相对路径
# （Debian 的 .so 链接很多是 /lib/aarch64-linux-gnu/... 绝对链，必须处理）
```

**符号链接是 sysroot 的头号坑**：`libc.so`、`libm.so` 等链接脚本/软链指向绝对路径 `/lib/aarch64-linux-gnu/...`，不重写会让交叉链接器悄悄用上 x86 的同名库。常用做法是用 `symlink rewrite` 小脚本或 `cp -L` 摊平后再重建相对链接；至少要在链接产物上抽查 `file` / `readelf -d` 确认没有把 x86 库链进去。

### 3.2 可以从宿主机 multiarch 仓库补的（开发板与发行版同源时）

Ubuntu/Debian 支持直接下载 arm64 deb 而不安装（避免真装 multiarch 污染宿主）：

```bash
# 宿主机：只下载不安装
apt-get download \
  libjson-c-dev:arm64 libnuma-dev:arm64 libpcap-dev:arm64 \
  libssl-dev:arm64 libdrm-dev:arm64 libasound2-dev:arm64 \
  libelf-dev:arm64 zlib1g-dev:arm64      # 后两个是 libdpdk.pc Requires.private（文档 01 §1.3 的“隐形依赖”）
for d in *.deb; do dpkg-deb -x "$d" $WS/sysroot/; done
```

要点：

- **与板子同一个发行版基座**（例如板上 Ubuntu 22.04 就用 22.04 的 arm64 deb），版本错配会以运行时符号缺失的形式爆出来；
- `libdrm-dev` 若发行版版本与板上 BSP 有出入，以板上导出的那份为准，multiarch 包只作兜底；
- `libjson-c-dev`、`libnuma-dev`、`libpcap-dev` 是 MTL 库层 + RxTxApp/app 层的必需项（文档 01 §3.1、§4 表）。

### 3.3 交叉编译自产的（构建顺序产物，回填 sysroot/staging）

| 产物 | 装到 | 下游消费者 |
| --- | --- | --- |
| patched DPDK（`libdpdk.pc` + 头） | `$WS/staging` | libmtl、所有下游 |
| xdp-tools/libbpf（`libxdp.pc`、`libbpf.pc`） | `$WS/staging` | libmtl（`MTL_HAS_XDP_BACKEND`）、MtlManager |
| `libmtl` + `mtl.pc` | `$WS/staging` | app、manager、RxTxApp、两个 rk3588 应用 |
| （可选）FFmpeg 7.0 arm64 | `$WS/staging` | mp4_dist、st22 场景 |

即：`mtl.pc`、`libdpdk.pc` 等**不需要**从板上拿——它们本来就由交叉构建自己产生，装进 staging 后由 `PKG_CONFIG_PATH` 暴露给下游。

### 3.4 pkg-config 三件套（每一层构建都要导出）

```bash
export PKG_CONFIG_SYSROOT_DIR=$WS/sysroot        # 所有 .pc 里的路径自动加此前缀
export PKG_CONFIG_LIBDIR=$WS/sysroot/usr/lib/pkgconfig:$WS/sysroot/usr/share/pkgconfig:$WS/sysroot/usr/lib/aarch64-linux-gnu/pkgconfig
export PKG_CONFIG_PATH=$WS/staging/lib/pkgconfig:$WS/staging/lib/aarch64-linux-gnu/pkgconfig   # 自产 .pc
```

- `PKG_CONFIG_LIBDIR` **必须显式覆盖**，否则宿主的 `/usr/lib/x86_64-linux-gnu/pkgconfig` 会漏进来，`json-c.pc` 之类的名字会命中 x86 版本——这是交叉编译最常见的静默错误源；
- 自产 `.pc`（mtl/libdpdk）里若有 `prefix=/usr/local` 之类绝对路径，配合 `PKG_CONFIG_SYSROOT_DIR` 通常已够用；若 DPDK 交叉安装时把 sysroot 路径写死进 `.pc`，检查一遍 `prefix/libdir` 是否合理。

## 4. 各层交叉构建步骤（顺序即依赖序）

### 4.1 patched DPDK（必做，不能省）

用 `script/build_dpdk.sh` 只取源码与补丁（文档 01 §2），交叉构建手工做：

```bash
# 1) 取源码 + 打补丁（可借用脚本逻辑，或手工）
curl -LO https://fast.dpdk.org/rel/dpdk-26.07.tar.xz
tar xf dpdk-26.07.tar.xz && cd dpdk-26.07
for p in $MTL_REPO/patches/dpdk/26.07/*.patch; do patch -p1 -i "$p"; done

# 2) 交叉配置（DPDK 自己也是 meson 工程，复用 aarch64.ini）
meson setup build-aarch64 --cross-file $WS/aarch64.ini \
  -Dplatform=generic \
  -Dcpu_instruction_set=armv8-a \
  -Denable_drivers=net/null,net/af_xdp,bus/pci,bus/vdev,common/iavf \  # 可再精简
  -Dtests=false -Dexamples= \
  --prefix=/usr/local
ninja -C build-aarch64 && ninja -C build-aarch64 install DESTDIR=$WS/staging
# 3) 检查 $WS/staging/usr/local/lib*/pkgconfig/libdpdk.pc 已生成
```

要点与风险：

- **NUMA 头必须在 sysroot**（`numa.h` 来自 `libnuma-dev:arm64`），否则 DPDK configure 失败；
- `-Dplatform=generic`：RK3588 不是 DPDK 认知的 SoC，generic + `cpu_instruction_set=armv8-a` 最稳；如果确定只在 RK3588 间部署，可试 `armv8.2-a`（Cortex-A76 支持的点），但**不要用 native**——交叉编译下 native 语义不明；
- 驱动精简是可选优化；文档 01 §2 的结论不变：即使走 AF_XDP/kernel 数据面，DPDK 的 EAL/mbuf/ring/ethdev API 仍被 libmtl 大量使用，**库本体必须完整链接**；
- `script/build_dpdk.sh` 的“已安装版本检测”在交叉场景直接跳过整个脚本即可——宿主机 pkg-config 环境已指向 sysroot+staging，检测语义也就自然对了；
- x86 的 ice/iavf 内核驱动补丁（`script/build_drivers.sh`）与交叉无关，跳过。

### 4.2 xdp-tools + libbpf（仅 AF_XDP 路线）

xdp-tools 是 make 体系，交叉方式：

```bash
cd xdp-tools-1.6.3
make CC=aarch64-linux-gnu-gcc \
     ARCH=aarch64 \
     BPF_CC=clang \
     PREFIX=$WS/staging
make CC=aarch64-linux-gnu-gcc ARCH=aarch64 BPF_CC=clang PREFIX=$WS/staging install
```

- libbpf/xdp-tools 内部的 BPF 程序编译用 clang（BPF 目标架构无关），用户态库用交叉 gcc；需要 sysroot 里有 `libelf`（libbpf 依赖，前面 deb 里已备）；
- 若板上 RK3588 内核的 BPF 能力不足（老 BSP 内核），可先退回 `kernel:` socket 数据面，跳过本步，libmtl 会静默降级为无 AF_XDP 后端——但**构建后必须断言是否真的编进了后端**（文档 01 RB2）：`grep MTL_HAS_XDP_BACKEND <build>/config.h` 或看 `meson configure` 日志；
- 本步完成后 `libxdp.pc`/`libbpf.pc` 在 staging，`PKG_CONFIG_PATH` 已覆盖。

### 4.3 libmtl（核心）

```bash
cd Media-Transport-Library
export MTL_INSTALL_PREFIX=$WS/staging       # 复用 build.sh 的约定？——不，手工 setup：
meson setup build-aarch64 --cross-file $WS/aarch64.ini \
  --prefix $WS/staging \
  -Dbuildtype=release \
  -Denable_tests=false        # gtest 不交叉（Cannot run test；如需单测见 §6）
  # 如不用 eBPF 探针：-Denable_usdt=false （等同 MTL_BUILD_DISABLE_USDT=true）
ninja -C build-aarch64 && ninja -C build-aarch64 install
```

要点与风险：

- **SIMD 探测自然退化**：meson 会探测 `-msse4.2/-mavx2/-mavx512*`，aarch64 gcc 一律拒绝，flag 不进命令行；`st_avx2.c`/`st_avx512*.c` 被 `#ifdef MTL_HAS_AVX2` 包裹，交叉下编译为空翻译单元（文档 01 §3.2），颜色转换走标量路径。**验证**：configure 日志中不应出现任何 `MTL_HAS_AVX*`；
- `-Werror`（非 debug 构建，文档 01 RB6）在 aarch64 gcc 上有一套**全新的告警集**，首次交叉编译大概率有新告警触发失败。定位时先临时 `-Dbuildtype=debugonly`（无 -Werror）把问题告警列出来，逐个修（多为 `printf` 格式串对 64 位类型的差异）；
- `-Denable_tests=false` 是因为 gtest 检测 + 单测执行在交叉下没有意义；若坚持交叉编 `UnitTest`，可 `libgtest-dev:arm64` 补进 sysroot，但**不能运行**；
- USDT：`dtrace` 是宿主工具可以继续用，但 `sys/sdt.h` 必须在 sysroot（`systemtap-sdt-dev:arm64` 可下载解包）；若镜像不打算用探针，直接 `-Denable_usdt=false` 最省事（RB3）；
- 产物：`$WS/staging/lib*/libmtl.so`、`$WS/staging/include/`、`mtl.pc`。

### 4.4 FFmpeg 7.0（仅 mp4_dist 需要；TX 想在 x86 上单独跑则不需要交叉版）

两种口径：

1. **接受板上发行版 FFmpeg**：sysroot 已带（§3.1），版本与 versions.env 的 7.0 不一致时，`mp4_dist` 代码对 4.4/6.x API 的兼容性需自查（`avformat` 基本接口稳定，风险低但需验证）；
2. **严格对齐 7.0**：x86 上 `./configure --enable-cross-compile --target-os=linux --arch=aarch64 --cross-prefix=aarch64-linux-gnu- --sysroot=$WS/sysroot --prefix=$WS/staging --enable-shared --disable-static --disable-x86asm` 后 make install。工作量可控（FFmpeg 官方支持交叉），但注意配套的编解码器开关按需裁剪。

### 4.5 MtlManager（AF_XDP 路线必做）

```bash
cd manager
meson setup build-aarch64 --cross-file $WS/aarch64.ini \
  --prefix $WS/staging
ninja -C build-aarch64 && ninja -C build-aarch64 install
```

- 宿主机的 `clang` + `llvm-strip` 继续用于把 `mtl.xdp.c` 编成 `mtl.xdp.o`（BPF 与目标机架构无关），但 libbpf 头/库来自 sysroot+staging——构建脚本里对 clang 的探测找到的是宿主 clang，能工作，前提是 sysroot 的 libbpf 头版本与板上内核 BPF 特性匹配；
- 若跳过 xdp-tools（§4.2 不做），MtlManager 会因找不到 libxdp/libbpf 而走无 XDP 分支，不需要 clang——此时 `mtl.xdp.o` 不会生成，板上 AF_XDP 后端自然不可用（与 RB2 一致，属预期）。

### 4.6 两个 rk3588 应用（真正的交付物）

```bash
cd app/rk3588_end2end
meson setup build-aarch64 --cross-file $WS/aarch64.ini && ninja -C build-aarch64

cd ../rk3588_mp4_dist
meson setup build-aarch64 --cross-file $WS/aarch64.ini \
  -Dbuild_tx=true -Dbuild_rx=true && ninja -C build-aarch64
```

- 依赖全部经 §3.4 的 pkg-config 环境解析：`mtl`/`libdpdk` 来自 staging，`rockchip_mpp`/`librga`/`libdrm`/`alsa`/FFmpeg 来自 sysroot；
- **必须做产物断言（RB5 在交叉下加倍成立）**：`test -x app/rk3588_end2end/build-aarch64/e2e_app` 等。交叉环境下“依赖缺失静默跳过”更容易发生（sysroot 少一个 `.pc` 都会触发），只看 `ninja` 退出码会漏检；
- `mp4_dist` 的 `build_rx=true` 带的 MPP 链接测试（`cc.links`）此时跑的是**交叉 gcc + sysroot**，是验证 MPP 头/库是否正确进 sysroot 的天然检查点——若这里失败，回查 §3.1 的导出与软链接改写；
- 每个应用各自的 `meson.build` 里没有 cross 感知逻辑，但也没有 x86 硬编码（与 `st22_avcodec` 的 `-msse4.2` 硬编码不同，见 RB4——该插件在交叉场景**明确跳过，不要编**）。

### 4.7 RxTxApp（验收框架用，可选）

`tests/tools/RxTxApp/` 是独立 meson 工程，交叉方式同 §4.6；产物是 aarch64 二进制，部署到板上供 pytest 验收框架（跑在 x86 宿主，通过 SSH 驱动板子）使用。注意它链接 `json-c`、`pcap`、可选 `sdl2`——**SDL2 交叉版很麻烦且板上无需显示**，可接受它静默跳过（对照文档 01 §4 表确认无强依赖）。

## 5. 部署到板子

```bash
# staging 整树 rsync（假设板上放 /opt/mtl-arm）
rsync -a $WS/staging/ board:/opt/mtl-arm/
# 板上运行时环境
export LD_LIBRARY_PATH=/opt/mtl-arm/lib/aarch64-linux-gnu:/opt/mtl-arm/lib
export PKG_CONFIG_PATH=/opt/mtl-arm/lib/pkgconfig   # 仅当板上还要再编东西
# DPDK 运行期（hugepages/AF_XDP 权限）仍按 doc/run.md / MtlManager 流程，交叉不改变运行期约束（文档 01 RB10）
```

验证产物架构：`file staging/**/*`（或抽查关键二进制）应为 `ELF 64-bit LSB ... ARM aarch64`；`readelf -d e2e_app | grep NEEDED` 确认没有混入 x86 库名。

## 6. 测试怎么办

| 层级 | 交叉下的可行性 |
| --- | --- |
| 单元测试（`build.sh unit`） | 可交叉**构建**，不能在本机**运行**。要跑就上 `qemu-user`（`qemu-aarch64 -L $WS/sysroot ./UnitTest`，配合 `-static` 或让 qemu 走 sysroot 的 ld-linux），CI 可行但工程量另计；P0 建议仍按文档 01 §6.1 口径在板上原生编译跑单测 |
| 集成测试（KahawaiTest） | 需真实 VF + root，本就与 x86 交叉无关；交叉产物直接部署板上执行 |
| pytest 验收 | 天然就是 x86 宿主 + SSH 板子的形态，交叉编译出的 `RxTxApp` 部署到 `.local_install` 对应路径即可复用（注意 const.py 的 PREFIX 约定，文档 01 RB8） |

## 7. 新增风险登记（承接文档 01 §7 的 RB 系列）

| ID | 风险 | 应对 |
| --- | --- | --- |
| RB11 | sysroot 软链接污染 | 绝对链接未改写时可能链到宿主 x86 库且**不报错**。导出脚本必须改写软链；产物用 `readelf -d` 抽查 NEEDED |
| RB12 | pkg-config 宿主泄漏 | `PKG_CONFIG_LIBDIR` 忘记覆盖时，`json-c` 等命中 x86 `.pc`，链接器报 architecture mismatch 或静默失败。构建前 `PKG_CONFIG_LIBDIR=… pkg-config --variable=libdir json-c` 验证 |
| RB13 | aarch64 gcc 新告警 × `-Werror` | 首次交叉失败几乎必然。用 `debugonly` 先收集告警清单，修完再回 release |
| RB14 | DPDK 版本检测被宿主 `libdpdk.pc` 干扰 | 交叉流程完全绕开 `build_dpdk.sh`，只借用它取源码+补丁（§4.1） |
| RB15 | 板上 FFmpeg 版本 ≠ versions.env 钉的 7.0 | 二选一：接受发行版版本并验证 `mp4_dist` API 兼容，或交叉自编 7.0（§4.4） |
| RB16 | 依赖缺失静默跳过（RB5 交叉放大版） | sysroot 缺 `.pc` 时 end2end 静默不生成 `e2e_app`。构建脚本强制产物存在性断言（§4.6） |
| RB17 | 交叉构建无 CI 背书（RB1 的交叉放大版） | 首次打通后把整条命令序列固化成脚本（如 `script/cross_build_rk3588.sh`）入库，锁版本、留日志 |
| RB18 | RK3588 BSP 内核 BPF 能力不足导致 AF_XDP 后端白编 | 构建后断言 `MTL_HAS_XDP_BACKEND`；不可用则退化 `kernel:` 后端，MtlManager 相应不带 `mtl.xdp.o`（RB2） |
