# DVS 节点内通信（`dvs_agent` ↔ `dvs_media`）问题清单与修改方案

> 范围：只讨论同一节点内代理与媒体引擎之间的本地 IPC，不动平台通道（见 `DVS_WS_CHANNEL_ISSUES_AND_FOLLOWUP_PLAN.md`），不动媒体数据面。
> 基准：当前工作树 `app/dvs_agent`（`media_ipc` 客户端、`main` 编排、`registration` 心跳）与 `app/dvs_media`（`ipc_server` 服务端、`state_machine`、`ipc_engine_bridge`、`layout_executor`）。
> 写作约束：只用自然语言描述改动，不贴完整代码；改动只做原模块内增量，不起替代性新模块；版本保持为 `1`，不做兼容层。

## 1. 通信现状结论

传输选择本身是合理的：同机控制面走 `Unix Domain Socket + JSON Line`，代理是唯一客户端（常连接、按需重连、一次重试），媒体是服务端（最多八连接、每连接一线程），与 `MTL/MPP/DRM` 数据面解耦，排障可直接用套接字抓行日志。

协议现状是两类语义并存：握手观测类（`hello` 版本核对、`capability` 上报、`query_state` 状态快照）与即时生效类（`configure` 直写角色与输出口、`tx_start/tx_stop` 输入角色启停、`clear`）工作正常；两阶段类（`prepare → commit/abort`）的状态机在媒体侧完整（空闲、准备中、已就绪三态加单调修订号，消息标识与操作标识双重幂等），但在代理侧没有走完，造成局部悬挂，这是本次方案要解决的核心。

## 2. 问题清单

### 两阶段悬挂

媒体的 `prepare` 成功后停留在已就绪态，必须由 `commit` 或 `abort` 回到空闲态，否则下一个 `prepare` 会被以另一操作进行中为由拒绝。代理的三处布局下发（短连接布局入口、长连接布局下行、手动准备入口）只发 `prepare`，从不发 `commit` 或 `abort`，且后台上报线程只向平台回执、不收尾本地状态。后果是首个布局 после 即把媒体锁在已就绪态，后续布局持续失败；手动运维也没有补救入口。

### 窗体形状与引擎形状脱节

平台下发的窗体形状（窗口数组加画布几何加生效时间）与引擎可执行的流形状（地址端口加码流尺寸）是两套字段。桥接层对窗体形状只做通过性校验、不暂存布局，提交时因无暂存而保持当前画面不变。测试也把该行为固化为符合预期。长远看画面切换没有真正发生，短期的屏障回执只代表接纳、不代表上屏，调用方容易误读为已切换。

### 生效时间字段名漂移

代理与平台使用 `applyAtNs`，媒体暂存读取的是 `applyAt` 或下划线变体，纳秒时刻在跨进程时丢失。即使后续补上按时提交，媒体也拿不到正确的目标时刻，只能立即切换，跨节点同屏的意义被削弱。

### 提交顺序与重放语义

媒体提交先推进状态机、再调用引擎落盘。引擎落盘失败时修订号已推进，调用方看到的是服务端错误，但状态已是已提交，重试会被当作重放直接成功，引擎失败被掩盖。重放成功时仍会再次调用引擎，虽然当前执行器幂等所以无害，但语义上重放不应有副作用。

### 广播持全局锁写

媒体广播逐个向客户端写时全程持有客户端表全局锁。一个慢客户端会拖住所有广播，其他客户端的提交应答与状态变更都会被连带阻塞。故障隔离缺失。

### 套接字权限未收紧

套接字文件创建后未显式收紧权限，依赖进程掩码。本机任意用户进程连接后即可下发清屏、启停推流等高危动词，与平台到代理的令牌防线不对等。

### 心跳重复查询引擎

代理每次心跳为组装上报而两次查询引擎状态，一次取媒体与时钟与通道摘要，一次取推流快照。同一份快照本可一次取回，现状使常态负载翻倍，高频心跳下更为明显。

### 包络双轨与运维缺口

对外平台契约与对内媒体协议各用一套包络命名与嵌套规则，准备结果事件把请求标识放在数据区而非包络，客户端须特判。手动运维只有准备入口，没有提交与中止的透传入口，排障时无法手工收尾悬挂操作。

## 3. 修改方案

### 媒体侧收尾与健壮性

* 提交改为先落引擎、再推进状态；进入时先识别已提交的重放，重放直接成功且不再触碰引擎；引擎失败则不推进状态，调用方可重试或中止。保持执行器幂等，使重放无副作用。
* 生效时间兼容三套键名，优先纳秒键，缺失时回退到旧键，保证跨节点同屏时刻可传递。
* 广播改为快照后逐个写：持锁只做活跃表快照，写时只持单连接写锁，不再持全局锁过阻塞写。慢客户端只影响自身。
* 监听成功后把套接字收紧为仅属主可读写，与代理同用户部署时默认安全，新人按默认部署即符合预期。

### 代理侧走完两阶段

* 后台上报线程在判定就绪或阻塞后，先向媒体发提交或中止、再向平台回执。提交失败时把就绪降级为阻塞并记日志，避免虚报。无平台地址的单机自治模式同样先收尾本地状态再返回，使手动与自主管线都不再悬挂。
* 新增提交与中止的透传入口，与现有准备入口同语义（透传引擎应答，不做二次解读），供排障与未来平台直驱提交复用，不新增业务分支。
* 心跳合并为一次引擎查询，媒体、时钟、通道、推流四部分从同一份快照组装。查询失败时各摘要填未知而非空，保证上行形状稳定。

### 契约与文档

* 窗体到流的真正翻译（按画布几何裁剪窗口、映射到收流会话）不在本次做，保持直通语义，在文档中明确准备回执仅代表接纳、不代表已上屏，避免调用方误读。翻译作为后续独立议题，另起方案。
* 包络统一（请求标识位置、事件包络）同样后移，先在新增透传入口与收尾逻辑中沿用现有包络，不做破坏性变更。
* 版本握手继续保持告警而非阻断（引擎可能晚于代理启动），以本方案的收尾与透传能力作为自愈手段，而非启动时硬拒绝。

## 4. 测试与验收

* 媒体单测沿用现有套接字端到端用例，覆盖准备重放单事件、提交重放不二次落盘、引擎失败不推进修订、窗体形状提交广播、通道数组超大包络不截断。
* 代理自测沿用现有无引擎自测，覆盖未配置与不可达的结构化信封、契约标识唯一、空地址不抛异常；新增心跳单查询的形状用例。
* 集成层面起一代理加一媒体（可用回环配置），连续下发两次布局，验证第二次不再被拒绝；杀引擎后重启，验证代理重连后可继续下发；单机模式下发一次，验证媒体回到空闲态。
* 长稳层面验证断平台网络后本地画面不受影响，恢复后屏障回执可继续上报。

## 5. 分工与顺序

先合入媒体侧的提交顺序、生效时间、广播快照、套接字权限四项，再合入代理侧的收尾提交、透传入、C单查询三项。前者是后者的前置（收尾依赖提交语义正确），后者合入后悬挂问题即闭环。窗体到流的翻译与包络统一留待后续方案，不在本轮实现。
