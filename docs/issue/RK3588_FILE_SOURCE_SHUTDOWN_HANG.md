# live_ingest 文件源分支超时不退出（feeder join 挂起）【已修复】

日期：2026-11-09。板上实测（RK3588，`live_ingest --source file`，loop 默认开启）。

## 1. 现象

- 单盒多节点验证 T1 首跑：RX 进程 30 秒正常结束，TX 进程超时 3 分钟仍存活，
  `wchan` 停在 futex 等待，主线程阻塞在线程 join，日志停在 MTL 初始化段
  （stdout 全缓冲，正常退出时的 `FILE:`/`video exit` 行永不落盘）。
- 必须 `pkill -9` 才能清理；残留进程继续占用 MTL 会话与 UDP 端口，
  影响后续轮次（端口冲突、MtlManager 配额）。
- HDMI 分支同等超时用法退出正常，只有文件源分支挂起。

## 2. 根因链

停机顺序与等待条件错配，共三环相扣：

- feeder 线程的循环条件是全局运行标志，只在信号处理函数里清零；
  超时倒计时结束并不清零，主线程随后直接进释放流程。
- 释放流程先 join feeder 线程，最后才停 MTL 会话。
  feeder 在帧缓冲池耗尽时会睡在发送宿的空闲等待上，
  该等待只看会话运行标志（释放后期才清零并广播）。
- 因此超时时刻 feeder 要么在循环里继续供帧（标志仍真），
  要么睡在空闲等待里（唤醒后看循环标志仍真，继续循环），
  join 永远等不到线程结束。

HDMI 分支无此问题：其管线有独立的运行标志，停机函数先清标志、
唤醒环形队列再 join，超时路径与信号路径一致。

音频 feeder 同理（ST30 发送宿的获取等待同样只看会话标志），
同一次修复一并覆盖。

## 3. 修改方案（已落地，原模块内）

- 在文件分支倒计时结束处先把全局运行标志置 false，再释放发送栈。
  语义为超时到期即停机请求，与信号语义统一。
- 时序安全性：置位后 feeder 循环即退出；短暂睡在空闲等待的线程
  会被仍在运行的 MTL 会话的帧回收唤醒一次，随后看到标志退出。
  音频线程同理（ST30 会话仍在运行，1ms 粒度唤醒）。
- 未改动停机顺序与发送宿本身；HDMI 分支不受影响。

## 4. 验证

- 重编 `live_ingest`（交叉编译服务器单次增量构建）并同步板端后，
  T1 30 秒轮次 TX 正常退出，`video exit` 行落盘，无残留进程。
- 全量回归 `all 40`（T0/T1/T2/T3）一次通过，超时退出全部正常。

## 5. 遗留

- 若 MTL 会话本身已停转（发送线程异常），睡在空闲等待的 feeder 仍可能
  等不到唤醒。当前判为极小概率（会话停转属于更严重的故障），
  暂不加停机顺序调整；若后续出现同类残留，优先查会话停转根因，
  而不是给等待加超时。
