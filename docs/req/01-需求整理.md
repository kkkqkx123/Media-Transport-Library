# DVS 项目需求整理

本文把散落在 `00-overview/`、`02-feature-map/`、`03-requirements/` 的 11 条 REQ 归并成一张可排期、可实现的需求全景，并抽出跨需求不变量，作为后续技术方案的输入。

## 1. 产品定位

DVS 是信息发布应用中的一个独立分布式视频墙控制模块。它把多台输入盒、输出盒和显示屏组织成“拼墙”，让任意一路实时信号被调度到任意显示区域。

产品有两个管理入口：

| 入口 | 载体 | 使用者 | 能力边界 |
| --- | --- | --- | --- |
| A 平台后台 | Web | 系统管理员、现场工程师 | 分组、拼墙、端口绑定、场景、开窗调度、设备管理 |
| B 节点本机后台 | 盒子自带 Web | 现场维护人员 | 仅管理该节点自身：角色、输入口、输出参数、网络注册、SIP、本机信息、重启/恢复/升级 |

大屏画面由输出盒直接输出，DVS 没有“用户运行态”页面。产品与信息发布的素材、节目、发布任务、排期不做业务融合；DVS 自有的播放任务只服务于视频墙。

## 2. 角色与权限

| 角色 | 主要诉求 | 权限口径 |
| --- | --- | --- |
| 系统管理员 | 搭结构、管设备、改配置 | 结构类（分组、拼墙增删改）与调度类都可用 |
| 现场工程师 | 日常开窗、切场景、排障 | 调度类可用；结构类只读 |
| 现场维护人员 | 单机排障、换角色、升级 | 登录节点本机页即获得单节点配置权限 |

权限规则在 REQ-0001～0007 中统一为：结构类仅管理员，调度类工程师可用。设备改名、退役、升级建议仅管理员（Q-OPS-01 待确认）。

## 3. 需求全景

## 4. 主流程

### FLOW-01 新装机到首次上屏

1. 盒子上电入网，节点代理向平台注册，设备列表显示在线。
2. 管理员建分组。
3. 在分组下建拼墙，选择类型、模式、行列、首格分辨率。
4. 进入传输配置，把输入盒加入白名单，分配组播地址。
5. 进入端口绑定，把输出盒拖到格位。
6. 进入画面页，把信号拖到画布，节点开始收流、解码、显示。
7. 保存为场景。

### FLOW-02 场景切换

1. 选择目标场景。
2. 平台检查全部绑定节点在线、已注册、时钟同步。
3. 平台下发 prepare，节点预建会话、预解码、预分配图层。
4. 全部 ready 后，平台下发统一 `apply_at`。
5. 节点在同一个全局帧边界切换本地布局并回执。
6. 全部回执同一 revision 后，页面更新当前场景。

### FLOW-03 误操作恢复

1. 一键清屏关闭全部窗口，保留底图。
2. 重新选择场景，按 FLOW-02 恢复布局。
3. 清屏本身不产生未保存改动。

### FLOW-04 单机维护

1. 维护人员直连盒子 IP，登录本机页。
2. 设置角色、输入口、输出分辨率与模式。
3. 配置网络与注册参数。
4. 查看本机信息，执行重启、恢复出厂或升级。
5. 节点重新注册，回到平台调度。

### FLOW-05 创建并执行播放任务

1. 在画面页创建任务，固定场景、拼墙、目标输出盒。
2. 任务进入待检查，平台校验节点在线、已注册、角色为输出盒、拼墙与场景可用。
3. 检查通过进入待执行；V1.0 仅支持立即执行。
4. 操作员开始执行，节点回执后进入播放中。
5. 结束后进入成功，当前播放投影清除，任务记录保留。

## 5. 跨需求不变量

这些规则被多条 REQ 引用，适合沉到平台公共层统一实现。

| 不变量 | 内容 | 落点 |
| --- | --- | --- |
| 单一真源 | 业务状态在平台服务；节点配置真源在节点本机页；播放任务唯一真源是 `dvs_playback_task` | 平台服务、节点代理 |
| revision | 每次保存或下发生成单调递增 revision；旧 revision 回执只写审计 | 平台 operation 服务 |
| operation | 跨节点或异步动作必须有 `operation_id`；所有阶段和节点回执共用 | 平台 operation 服务 |
| 幂等 | 写请求带 `Idempotency-Key`；重复请求返回首次结果 | 平台 API 网关 |
| 过期 | 操作有 `expires_at`；过期后必须新建，不补发旧命令 | 平台 operation 服务 |
| 能力回读 | 端口、分辨率、刷新率、同步能力只认节点上报，不用页面硬编码 | 节点代理 |
| 删除语义 | 分组硬删、拼墙软删 7 天、场景按生效状态保护、节点退役 30 天墓碑 | 平台服务 |
| 离线保画 | 控制链路断开时节点保持最后有效画面；媒体流可继续 | 媒体引擎 |
| 未保存改动 | 编辑立即上屏，不写已保存场景；离开时二选一：另存新场景或放弃 | 平台 + 前端 |
| 同帧 | 任一目标节点异常则整墙阻止；不做部分切换 | 平台 + 节点 |

## 6. 需求分层

按实现职责分成四层，便于分工和排期。

| 层 | 职责 | 对应需求 | 技术选型 |
| --- | --- | --- | --- |
| 业务控制层 | 分组、拼墙、设置、白名单、场景快照、播放任务、设备管理 | 0001–0003、0005、0010、0011 | 平台后端 + 关系库 + REST/WS |
| 实时控制层 | operation/revision、prepare/commit、节点回执聚合、时钟资格 | 0005、0006、0007、0011 | 平台后端 + 消息通道 |
| 媒体数据层 | 采集、编码、组播收发、解码、裁剪缩放、图层合成、音频 | 0003、0004、0006、0011 | MTL + MPP + RGA + DRM + ALSA |
| 节点设备层 | 角色、输入口、输出模式、网络、注册、SIP、本机页、升级 | 0008、0009、0010 | 节点代理 + 固件 |

## 7. 需求成熟度与缺口

### 7.1 状态

- 11 条 REQ、11 个 PAGE、验收与测试用例当前全部为 `draft`。
- 8 个 P0 开放问题未关闭，集中在硬件能力、同帧时基、规模压测、NFR 阈值、固件升级、角色切换原子性、设备退役、拼墙删除。
- 现有文档已经把业务规则写得较完整，缺口集中在可验证的技术证据。

### 7.2 技术缺口

| 缺口 | 影响 | 建议 |
| --- | --- | --- |
| 整机端口、分辨率、HDCP/EDID 未实测 | 节点能力、输出预设、兼容性无法定稿 | 先做硬件能力矩阵实测，节点上报 capabilities |
| 同帧时基与 ≤1 帧偏差未验证 | REQ-0005/0006/0011 的核心验收无法关单 | 两节点 PTP + 1000 次切换实测 |
| 128 节点、64 墙、64 窗口未压测 | 容量基线无法确认 | 节点模拟器 + 混合负载压测 |
| 千兆网络承载方案未定 | 压缩/未压缩、画质、时延无法定稿 | 先做带宽核算与两节点码流实测 |
| 跨格拆分算法未定义 | 开窗跨格无法实现 | 本文给出坐标系与拆分规则，评审后固化 |
| 节点媒体引擎未产品化 | MTL 参考应用不能直接量产 | 抽公共库、补状态机、补测试 |
| 播放任务与媒体动作的关系未定义 | 任务状态可能和画面不一致 | 任务作为场景切换 operation 的上层封装 |

## 8. 需求归并结论

从实现角度看，11 条 REQ 可以归并成 6 个工程域：

1. 平台资源模型：分组、拼墙、设置、白名单、绑定。
2. 场景与窗口模型：快照、窗口、音量、布局模式、未保存改动。
3. 实时操作框架：operation、revision、prepare/commit、回执、过期。
4. 节点媒体引擎：采集编码、组播收发、解码合成、音频。
5. 节点代理与设备生命周期：注册、心跳、能力、本机页、升级、退役。
6. 平台前端：分组列表、拼墙列表、设置面板、画面页、设备列表、节点本机页。

其中第 3、4 域是技术风险最高的部分，也是 MTL 发挥作用的重点。
