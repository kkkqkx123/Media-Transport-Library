# 文件源默认码流上限丢弃高码率 IDR 帧【已规避】

日期：2026-11-09。板上实测（`/usr/local/test.mp4`，平均 6.8Mbps，1080p24）。

## 1. 现象

- T1 首跑（发送侧默认配置）：30 秒供帧 730，进 4 帧丢弃。
  丢弃率约 0.5%，但判定要求零丢弃，首跑未通过。
- 丢弃集中在个别大帧，不是均匀分布；收流侧零坏帧，
  说明丢的是发送侧主动放弃的帧，不是链路损伤。

## 2. 根因

- 文件 feeder 对每帧做上限检查：拼接后尺寸超过码流上限即计数丢弃，
  不送发送宿。发送侧码流上限默认 512KB。
- 该片源平均帧仅约 35KB，但 IDR 大帧可达数百 KB，
  峰值超过 512KB 即被丢弃。接收侧码流上限默认 1MB，
  发送侧默认只有接收侧一半，两侧默认值不对称是主因。
- 这是已知行为（码流上限偏小会截断高码率帧），不是回归：
  高压缩效率片源的 IDR 峰值平时不易触线，6.8Mbps 的 1080p 片
  恰好能探到这条边界。

## 3. 修改方案（验证配置侧，已落地）

- 文件 TX 改用 JSON 描述（含 1MB 码流上限，与接收侧默认值对齐），
  由验证脚本按端口与片源路径渲染后下发，不再用 CLI 默认值跑文件源。
- 生产侧不改默认值：512KB 默认仍保留，按需调大是部署配置，
  不是程序缺陷。验证脚本里固定 1MB 是为了让虚拟节点不因默认上限
  引入额外变量。
- 判定保持零丢弃：上限对齐后 T1/T2 文件源供帧丢弃均为 0。

## 4. 验证

- T1 改后：730 帧 0 丢弃；T2 文件 lane：970 帧 0 丢弃。
- 若后续换高码率片源（如 40Mbps），IDR 峰值可能再超 1MB，
  届时按片源实际峰值上调上限并记录，不放宽零丢弃门限。

## 5. 遗留

- 发送宿帧缓冲为 8 帧定额， feeder 以缓冲池为节流器、
  MTL 会话按帧率消费，属背压设计而非 pacing 设计。
  大帧堆积时表现为 feeder 短暂驻留而非丢弃（上限内），
  长稳轮次可观察驻留时长分布，本轮未展开。
