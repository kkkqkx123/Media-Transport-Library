# RK3588 应用与 DVS 应用融合技术方案

> 基准：仓库当前工作树（`feat/rk3588-apps` 之后的 DVS 阶段），MTL `26.09.0.DEV`
> 范围：V1.0 单节点多窗口、2~4 节点墙、prepare/commit 同帧、底图与音频归属

---

## 1. 目标

四层职责：

| 层 | 职责 |
|---|---|
| 平台控制面 `dvs_platform` | 业务模型、快照、revision、operation、布局像素拆分、审计 |
| 节点代理 `dvs_agent` | 注册、心跳、六 scope 配置状态机、本机页、媒体控制转发 |
| 节点媒体引擎 `dvs_media` | 采集/编解码/收发/合成/音频/PTP/DRM/ALSA |
| MTL | ST2110 协议栈、PTP、组播、pacing、冗余 |

---

## 2. 现状（开发与过渡形态）

当前仓库存在三个 RK3588 相关应用：`rk3588_live_tx`、`rk3588_playout_rx`、`dvs_media`。其中 `dvs_media` 通过 in-tree 编译复用另外两个应用的源码，output 角色基本可用，input 角色已接入 rk3588 app 的 TX 数据面，但 teardown、能力门控与切换验证仍不完整。`both` 模式仅用于开发/回环，不交付生产镜像。

平台与代理当前通过 HTTP REST over TCP 交互；WS/gRPC 属于目标架构，不是当前实现。

当前仅验证了内核后端、Generic XDP模式（在内核协议栈的 netif_receive_skb() 之后挂载），AF_XDP需要修改内核代码中网卡驱动部分(docs/issue/RK3588_DRIVER_ISSUES.md)【缺少`ndo_bpf`, `ndo_xdp_xmit`, `XDP_SETUP_PROG`的实现，导致`mt_dev_xdp_init`: `Underlying driver does not support XDP in native mode`】，仅启用XDP选项还不够，需要补驱动的实现。等到定昌提供新SDK再进一步确认。如果无法解决，就使用内核模式

---

## 3. 最终生产架构

- 节点媒体引擎统一为单一 `dvs_media` 包，运行时选择 input 或 output 角色。
- 角色互斥：一个节点同一时刻只运行采集/编码/TX 或接收/解码/合成/显示中的一组数据面。
- MTL 在进程内初始化一次，同时持有 RX 与 TX 端口，供角色切换复用。
- 共享基础设施通过正式库依赖提供，不采用源码目录级 in-tree 复用作为生产构建方式。
- 生产部署按节点能力与配置选择角色；能力不足时拒绝角色切换。
- rk3588 app 保留为验证与回归入口，不作为生产交付物。

---

## 4. 关键约束

- **PTP 时钟**：全网统一 PTP 域，节点读取 `CLOCK_TAI`，同帧提交基于全局帧号。PTP 偏差超阈值时，节点应拒绝新的同帧操作，但保持已有画面。
- **网络带宽**：千兆网络下默认采用 ST2110-22 压缩视频；未压缩方案仅作为可选配置。带宽不足会导致丢帧、画质下降或无法承载多路信号。
- **软件 pacing**：ARM 平台使用软件 pacing；AF_XDP native 模式受驱动限制时走内核后端。软件 pacing 对 CPU 负载和调度延迟更敏感。
- **进程隔离**：数据面不得调用控制面阻塞代码；媒体引擎与代理保持进程分离，避免控制请求破坏实时媒体链路。

---

## 5. 实施路径

实施路径按风险从低到高推进：先证明基座可运行，再做单节点媒体引擎，再做平台控制面，最后做同帧与规模化。每个阶段都有明确退出标准，避免在未验证基座的情况下推进复杂功能。

1. P0：完成 RK3588 基座验证（MTL、PTP、组播、MPP/DRM/ALSA、单路稳定运行）。
2. P1：完成 `dvs_media` output 角色 MVP，并把 input 角色的数据面模块接入同一媒体包。
3. P2：完成平台业务模型、节点网关与两节点 operation 闭环。
4. P3：完成同帧提交、跨格拆分、影子布局与 rollback。
5. P4：完成节点运维、设备管理、规模化与加固。

输入角色接入插入 P1/P2 之间：先完成 MTL 双端口初始化与数据面模块接入，再补齐 teardown、能力门控与单板冒烟。

## 6. 待决策问题

以下问题影响架构、部署与运维边界，需要在评审时明确。概念说明用于帮助判断，不代表最终结论。

| 问题 | 概念说明 | 当前建议 |
|---|---|---|
| 压缩与不压缩 | ST2110-22 使用 H.264/HEVC 等压缩视频，带宽低但受 GOP 和编码时延影响；ST2110-20 使用未压缩视频，时延最低且无 GOP，但带宽高，千兆网络通常无法承载 1080p60 以上。 | V1.0 默认 ST2110-22 压缩；无传输瓶颈时可选未压缩 |
| 编码格式 | H.264 兼容性好，适合 1080p；HEVC 压缩率更高，适合 4K；JPEG XS 时延低但需要编解码支持。 | H.264 1080p，HEVC 4K；有 JPEG XS 硬件时优先 |
| GOP 策略 | GOP 决定关键帧间隔，影响场景切换等待时间与带宽；短 GOP 切换快但带宽更高。 | 0.5–1 秒，可配置 |
| 组播模式 | SSM 指定源组播可过滤非法源，安全性更高，但需要源地址与网络配置；ASM 配置简单但安全性较弱。 | SSM，指定源 |
| PTP 来源 | PTP 为全网统一时基；外部 linuxptp + CLOCK_TAI 与 ST2110 体系一致，但需要网络与硬件支持。 | 外部 linuxptp + CLOCK_TAI |
| 合成方式 | DRM plane 直接合成效率高、时延低，但受硬件 plane 数量限制；GPU/RGA 兜底可支持更多窗口，但增加处理时延。 | DRM plane 优先，GPU/RGA 兜底 |
| 控制通道 | HTTP REST 易调试、实现简单；WS/gRPC 可支持长连接、推送与更高吞吐，但复杂度更高。 | 当前 HTTP REST；目标 WS，必要时评估 gRPC |
| MTL 维护方式 | fork + 固定 tag + 补丁可控制变更，但需要自行维护；直接跟踪上游升级快但风险高。 | fork + 固定 tag + 补丁 |
| 单节点多输出口 | 多输出口可支持多显示器，但会增加 DRM connector、绑定模型与能力校验复杂度。 | V1.0 单口优先 |
| 角色切换方式 | 运行时切换可避免重装镜像，但需要完整 teardown、能力门控与资源释放；固定角色包更简单但运维成本高。 | 统一媒体包 + 运行时角色选择 |

## 7. 验收基线

验收基线用于判断系统是否达到 V1.0 可用状态。

- 单屏 4 路 1080p60 合成显示（物理 HDMI 输出口数量以实际硬件为准），窗口可移动、缩放、调层序。
- 两节点 2×1 墙走通 FLOW-01。
- 2×2 墙 1000 次切换偏差不超过 1 帧。
- 任一节点离线时整墙阻止，画面不变；commit 失败自动 rollback。
- 媒体引擎重启 30 秒内恢复最后布局。
- 输入与输出角色均可运行，角色切换具备资源释放与能力门控。
