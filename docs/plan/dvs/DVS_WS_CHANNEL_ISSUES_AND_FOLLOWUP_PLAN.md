# DVS 平台—代理 WS 通道遗留问题与后续修改方案

> 范围：只讨论 `dvs_agent` 与 `dvs_platform` 之间的控制通道（WS 长连接与 HTTP 短连接），不动 `agent—media` 本地 IPC，不动媒体数据面。
> 基准：`docs/plan/dvs/DVS_PLATFORM_AGENT_WS_GRPC_DESIGN.md`（目标拓扑与迁移策略），现状以当前工作树 `app/dvs_common|dvs_agent|dvs_platform` 为准。
> 写作约束：本文件只用自然语言描述改动，不贴完整代码；改动只做原模块内增量，不起替代性新模块。

## 1. 现状结论

通道迁移已基本落地，但属于双模并存而非单模切换：

- 承载已切：平台同端口双服，流式路径为新增的通道路径；代理为唯一拨号方，断线由代理退避重拨；下行扇出优先走长连接推送，无连接才回退反向短连接回调。
- 契约已收敛到公共模块：消息类型、信封形状、消息标识生成、鉴权入口、必填字段校验、协商缺省全部在 `dvs_common` 的契约职责内，两端同源编译，非法直接拒绝。
- 六类消息中问候、心跳、布局下发、配置下发、升级任务已实现双通道同语义；三类上行回执不对称，其中屏障回执有回退但存在重复投递，配置确认与升级进度仅有长连接路径。
- 传输选择由环境变量控制，缺省为优先长连接失败回退短连接，另有仅长连接与仅短连接两档，平台按节点记录实际传输类型用于灰度观察。

## 2. 问题清单

### 契约与校验不对称

- 短连接入口基本不走共享校验，长连接入口全量校验。同一份心跳载荷在长连接上会被拒绝，在短连接上会被接受，校验强度取决于走了哪条路。
- 布局下发实际使用的生效时间字段未纳入契约校验表，收发双方已在使用但契约不约束，属模式漂移。
- 配置下发的允许键集合在契约、平台扇出过滤、代理落库三处各写一次，新增键时容易只改一处。
- 公共模块说明文档仍只描述传输与存储，未提及契约职责，新人按文档会漏掉契约。

### 上行回执不对称与重复投递

- 屏障回执的上行 helper 内部已含短连接回退，但其调用方在回退失败后又再发一次短连接提交，形成同一回执发两次。屏障状态机虽可收敛，但审计与回执计数会被污染。
- 配置确认的上行 helper 在无长连接时直接丢弃，不回退短连接。短连接模式下平台永远收不到确认。
- 升级进度的上行 helper 同上，无长连接即丢弃。短连接模式下升级任务下发了但进度回不来。
- 长连接问候的回执与短连接注册的回执形状不同，一个回协商参数，一个回完整节点文档，调用方需记两套形状。

### 连接注册与推送并发

- 平台连接注册表用节点标识到连接句柄的内存索引，替换旧连接时在锁内做连接关闭操作，慢连接会拖住注册表。
- 推送先查句柄再加发送锁发送，查与发之间连接可能已被替换或关闭，存在发到过期句柄的窗口。
- 全局单发送锁串行化所有节点的下行，一个慢节点会阻塞其他节点的布局与心跳确认，批量扇出时队头阻塞明显。
- 大消息与小消息共用同一发送路径，升级任务这类大载荷可能挤占布局与心跳的发送时机，设计中要求的按类型限长尚未实现。

### 代理侧会话与计时

- 代理的传输类型标记被循环线程与查询方共享但无同步保护，存在数据竞争。
- 代理接收循环以心跳周期加余量为超时，超时即补心跳；计时基于秒级时钟换算为毫秒，抖动大，弱网下可能出现心跳风暴或误判断开。
- 代理发送加锁但接收与关闭不完全串行，关闭与接收竞态时可能误判为传输错误而重拨。
- 平台侧空闲判定靠连续错过心跳加主动探活，代理侧靠接收超时补心跳，两边超时与探活周期未统一协商，中间设备回收空闲连接时两端感知延迟不一致。

### 可观测与运维

- 平台按节点记录传输类型，但下行究竟走了哪条路只记审计不回给调用方，排障需翻审计。
- 幂等重放只在平台侧有界缓存，代理侧无重放缓存，平台重发下行时代理会重复执行一次再回确认。
- 固件上传等大体量传输按设计应走短连接不挤占长连接，现状已如此，但未在文档中明确为长期分工，容易被误改为走长连接。

## 3. 修改方案

### 公共契约与传输职责

- 契约补齐生效时间字段的约束，使布局下发的校验表与实际发送字段一致。
- 收敛配置下发的允许键到契约一处，平台过滤与代理落库只读契约的判定结果，不再各自硬编码键名。
- 短连接的注册、心跳、提交入口复用与长连接相同的校验函数，校验失败返回同一形状的失败信封，使双通道同语义落到代码而非注释。
- 传输层增加按消息类型限长的发送队列语义说明，大载荷任务与小控制消息分开排队，超限时丢弃非关键遥测而保留屏障与配置。实现仍在原传输文件内增量，不新增模块。
- 更新公共模块说明文档，补上契约职责一节，使文档与代码一致。

### 代理侧

- 上行回执统一为先走长连接、无长连接走短连接的两档，不再由调用方二次补发。屏障回执保留回退，配置确认与升级进度补上短连接回退，回退目标复用现有短连接提交与状态上报语义，不新增端点。
- 删除布局事件监听处的重复提交逻辑，只保留上行 helper 内的一次投递语义，调用方只判断是否送达传输层。
- 传输类型标记改为原子量或在原互斥下读写，消除数据竞争。
- 接收超时与心跳发送统一用单调时钟，超时补心跳前先确认已超过半个周期，避免把传输错误误判为超时。关闭与接收的句柄校验放在同一把发送锁或会话代次下做，防止关闭竞态误重拨。
- 问候载荷继续复用短连接注册体的构造逻辑，使两路注册体同源，避免字段分叉。

### 平台侧

- 连接替换时只在锁内做索引切换，旧连接的关闭移到锁外，避免慢关闭阻塞注册表。
- 推送改为在发送锁内完成查句柄加发送，或引入按连接的发送队列，使查与发原子化；全局单锁拆为按连接锁，慢节点只阻塞自身。
- 屏障投递结果明确区分为已发送与无连接两类，无连接节点记入缺席集合并随准备回执返回，调用方可直接看到扇出结果，不再只记审计。
- 升级任务队列保留逐节点串行与失败隔离，发送前仍先做契约校验，校验失败即记审计跳过，不再尝试短连接。
- 到期屏障的超时回收保留现有后台扫描语义，超时按阻塞处理并生成回滚，避免永久停留准备中。

### 测试与文档

- 单元层面补短连接入口的校验用例、回执双通道用例、连接替换与慢接收者的推送隔离用例。
- 集成层面起一平台加双代理跑建组建墙开窗全流程，覆盖断线重连、超时回滚、无连接缺席、令牌错误拒绝、升级进度回传，并对比两种传输模式下的行为一致。
- 长稳层面验证断控制网络后媒体画面不受影响，恢复后自动重连并追平版本。
- 回写公共模块文档与本方案的验收指标，使真相源唯一。

## 4. 旧短连接模式是否应该放弃、双模式是否有必要保留

结论是短连接不应完全放弃，但应从双主降级为分层保留：长连接做节点控制通道的首选，短连接做三类明确用途的保留路径。理由如下。

值得保留的方面：

- 本机运维与浏览器管理面本来就是短连接语义，节点本机接口与平台文档增删改查与审计查询与静态页面服务与本机关联调试都适合短连接，长连接替代不了。
- 大体量传输适合短连接，固件上传等大载荷走短连接可避免挤占控制长连接的发送时机，长连接只走小而高频的控制消息更稳。
- 灰度与逃生需要短连接，传输模式环境变量提供的仅短连接档是中间设备回收空闲连接、弱网、联调抓包时的逃生开关，去掉即失去回退手段。
- 平台反向可达兜底需要短连接，在长连接尚未建立或刚断开的窗口内，平台仍需经注册上报的可达地址做一次性下发，否则新节点永远无法被首次触达。

不应保留的方面是双主语义：

- 双主意味着两套校验、两套回执、两套文档写入路径，现状已出现校验强度不一致与回执丢失，长期双主会持续分叉，测试矩阵翻倍。
- 调用方不应感知两套形状，问候回执与注册回执、长连接确认与短连接确认应逐步对齐为同一数据子集的不同承载。

建议分工：

- 节点控制通道默认走长连接，缺省传输模式保持优先长连接失败回退短连接；稳定局域网可切仅长连接，联调排障可切仅短连接。
- 平台对外编排接口与节点本机运维接口永久保留短连接；平台到节点的布局、配置、升级下发与节点到平台的心跳、回执、进度优先走长连接，短连接仅作回退逃生。
- 大体量传输长期走短连接，不迁入长连接。
- 下行投递结果显式返回走了哪条路并记传输类型，使灰度可观测；待双通道行为一致且长稳达标后，再评估是否在特定局域网内部署中默认关闭回退，但保留开关本身。

## 5. 验收标准

- 任一传输模式下注册、心跳、布局、回执、配置、升级六类消息的字段约束一致，非法载荷在双通道均被拒绝。
- 短连接模式下配置确认与升级进度不再丢失，屏障回执单次投递语义成立。
- 慢节点不阻塞其他节点的下行与心跳确认，连接替换不丢新连接的首次问候。
- 传输模式三档切换无需改数据格式，回退只需切换环境变量。
- 文档与代码一致，公共模块文档包含契约职责，验收指标可复现。

## 6. 风险与不做事项

- 空闲连接被中间设备回收仍是主要风险，保活周期应小于常见回收超时，超时与探活周期两端统一。
- 不引入新的运行时依赖，不做加密证书体系与多语言桩生成，不合并平台与代理进程，不让平台直连媒体引擎。
- 不做跨格语义与同帧提交等媒体侧任务，那些由引擎与布局方案另行覆盖。
